# 패션 데이터 프로젝트 실행: 수집·워크플로우·역할

앞 장에서는 운영 데이터를 분석 가능한 상태로 준비하고 고객·상품·판매 데이터를 연결하는 원리를 살펴보았다. 그러나 실제 프로젝트에서는 내부 데이터만으로 충분하지 않을 수 있고, 분석 결과를 리포트나 서비스로 전달하려면 여러 단계와 역할을 조율해야 한다.

> **이 장의 중심 질문**<br>
> 필요한 데이터를 어디서 확보하고, 비즈니스 질문에서 결과 활용까지 어떤 순서로 진행하며, 누가 각 단계를 책임져야 할까?

## 학습 목표

이 장을 마치면 다음을 설명할 수 있다.

- 회사 안팎의 데이터를 상황에 맞게 확보하는 방법
- 기존에 없던 데이터를 조사나 실험으로 만드는 이유
- 비즈니스 질문에서 리포트 또는 서비스까지 이어지는 분석 워크플로우
- 분석 결과를 사람이 활용하는 경우와 시스템이 활용하는 경우의 차이
- 데이터 엔지니어·데이터 분석가·데이터 과학자·머신러닝 엔지니어와 패션 실무자의 역할 차이

## 1. 데이터를 확보하는 다섯 가지 상황

필요한 데이터를 가져오는 방법은 하나가 아니다. 먼저 이미 존재하는 데이터를 확인하고, 질문에 꼭 필요하지만 없는 데이터만 추가로 수집한다.

### 상황 1. 회사 내부에 이미 존재하는 데이터

주문 DB, 고객 DB, 상품 DB, ERP, CRM, 재고 DB와 클릭 로그를 먼저 확인한다. 이미 운영 중인 데이터는 새 조사보다 추가 구축 비용이 적고 실제 업무 행동과 직접 연결되어 있다는 장점이 있다.

다만 존재 여부만으로 충분하지 않다. 분석 기간의 이력이 보존되는지, 식별자가 일관적인지, 개인정보 이용 범위가 적절한지 함께 확인한다.

### 상황 2. 쇼핑몰 플랫폼에서 제공하는 데이터

Cafe24나 Shopify 같은 플랫폼의 관리자 화면에서 주문 데이터를 CSV로 내려받을 수 있고, 반복 작업이라면 API로 자동 수집할 수도 있다.

**API(Application Programming Interface)**는 다른 시스템에 정해진 형식으로 요청하고 응답받는 창구다. 제공 항목, 접근 권한, 호출 횟수, 보안 정책을 먼저 확인해야 한다.

### 상황 3. API를 사용할 수 없는 경우

현실에서는 Excel·CSV, 이메일 첨부, 보안 USB, 사내 공유폴더로 데이터를 전달받기도 한다. 기업 규모, 기존 시스템, 협력사 관계와 보안 정책에 따라 전달 방식은 다양하다.

이 경우 파일 버전, 기준 날짜, 컬럼 의미와 작성자를 함께 기록하지 않으면 같은 분석을 재현하기 어렵다.

### 상황 4. 회사 밖에 있는 외부 데이터

경쟁사 상품·가격, 날씨, 트렌드, SNS와 검색 결과처럼 내부 DB에 없는 정보는 공개 API, 공개 데이터, 적법한 크롤링이나 데이터 구매로 확보할 수 있다.

**크롤링(crawling)**은 웹페이지의 정보를 프로그램으로 읽어 필요한 항목을 모으는 방법이다. 기술적으로 읽을 수 있다는 이유만으로 수집해서는 안 되며, 이용약관·저작권·개인정보·접근 제한과 수집 목적을 확인해야 한다.

### 상황 5. 아직 존재하지 않는 데이터

“할인 배너를 빨간색으로 바꾸면 구매율이 증가하는가?”라는 질문은 기존 주문 DB만으로 답하기 어렵다. 빨간 배너를 본 고객의 결과가 아직 없기 때문이다. 이때는 조사나 실험으로 필요한 데이터를 새로 만든다.

**A/B Test**는 비슷한 고객을 두 집단으로 나누어 한 가지 조건만 다르게 보여주고 결과를 비교하는 방법이다.

## 2. 먼저 비즈니스 질문과 데이터 점검을 정의한다

분석 프로젝트의 첫 질문은 “어떤 데이터를 가져올까?”보다 **“무엇을 알고, 어떤 결정을 바꾸려는가?”**에 가깝다.

“매출을 높이자”는 범위가 너무 넓다. “최근 3개월 동안 첫 구매 고객의 30일 이내 재구매율이 낮아진 이유는 무엇인가?”처럼 대상·기간·행동과 의사결정을 구체화해야 필요한 데이터도 정할 수 있다. 이것이 **비즈니스 질문**이다.

질문을 정한 다음에는 회사가 이미 가진 데이터를 점검한다. 이를 **데이터 점검(Data Audit)**이라고 한다.

1. 필요한 데이터가 실제로 존재하고 과거 이력이 보존되는가?
2. 어디에 저장되어 있고 누가 접근할 수 있는가?
3. 파일·DB·API·이미지 등 어떤 형태인가?
4. 공통 Key와 시간 정보로 서로 연결할 수 있는가?
5. 누락·중복·취소·반품과 지표 정의를 확인할 수 있는가?

## 4. 같은 분석 결과도 리포트와 서비스는 다르다

고객·상품·판매 데이터를 연결해 다음과 같은 패턴을 발견했다고 하자.

> **관측 기간에는 강남 지역 30대 직장인 집단에서 20만 원대 남색 오버사이즈 코트의 구매 비중이 높았다.**

### 리포트로 활용

사람이 결과와 한계를 읽고 판단한다. 상품기획팀은 다음 시즌 상품 구성을 검토하고, 마케팅팀은 캠페인 대상과 메시지의 가설을 세운다.

### 서비스로 활용

분석 규칙이나 모델이 시스템 안에서 작동한다. 조건에 맞는 고객과 상품을 찾고 추천 결과를 노출하거나 CRM 메시지 후보를 만들 수 있다. 자동 실행 전에는 동의 범위, 오류 대응, 성과 감시와 중단 기준이 필요하다.

## 5. 워크플로우 안에서 일하는 사람들

데이터 직무는 서로 완전히 분리된 섬이 아니다. 같은 프로젝트의 다른 구간에 더 큰 책임을 가진다.

| 역할 | 주된 책임 | 패션 이커머스 예 |
|---|---|---|
| 데이터 엔지니어 | 수집·저장·통합·파이프라인 | 주문·클릭 로그를 매일 적재하고 식별자 품질을 관리함 |
| 데이터 분석가 | 점검·정제·탐색·대시보드·리포트 | 고객 집단별 구매와 반품 차이를 요약함 |
| 데이터 과학자 | 통계·예측·세분화·추천 | 구매 가능성이나 추천 점수를 추정하고 검증함 |
| 머신러닝 엔지니어 | 모델 서비스·운영·감시 | 추천 모델을 쇼핑몰에 연결하고 안정적으로 운영함 |
| 패션 MD·마케터 | 질문·업무 해석·의사결정 | 상품 구성·가격·캠페인 실행에 결과를 적용함 |

아래 내용은 고정된 조직도가 아니라 **한 프로젝트에서 누가 어느 단계에 더 큰 책임을 갖는지** 보여주는 역할 지도다. 회사 규모와 프로젝트 성격에 따라 책임은 겹칠 수 있다.

### 질문과 지표를 정할 때

패션 MD·마케터는 업무 요구와 성과 기준을 제시하고, 데이터 분석가는 측정 가능한 질문인지 검토한다. 데이터 엔지니어는 필요한 데이터가 실제로 존재하는지 확인한다. 예측이나 자동화가 필요하다면 데이터 과학자는 모델 목표와 평가 방법을, 머신러닝 엔지니어는 지연 시간과 운영 환경 같은 제약을 함께 검토한다.

### 데이터를 점검하고 확보할 때

패션 실무자는 숫자만으로 알기 어려운 업무 맥락을 설명한다. 분석가는 품질과 누락을 점검하고, 데이터 엔지니어는 수집·저장·식별자 규칙을 설계한다. 데이터 과학자는 라벨과 표본 편향을, 머신러닝 엔지니어는 서비스에서 입력을 제때 받을 수 있는지 확인한다.

### 데이터를 통합하고 정제할 때

패션 실무자는 용어와 업무 규칙을 확인하고, 분석가는 질문에 맞는 분석용 데이터를 구성한다. 데이터 엔지니어는 파이프라인과 JOIN을 운영한다. 모델을 만든다면 데이터 과학자는 학습 데이터를 구성하고, 머신러닝 엔지니어는 학습 때와 서비스 때의 데이터 정의가 일치하는지 점검한다.

### 분석하고 검증할 때

분석가는 집계·비교·시각화를 수행하고, 데이터 과학자는 통계·예측·실험으로 가설을 검토한다. 데이터 엔지니어는 같은 결과를 다시 만들 수 있는 데이터를 제공한다. 패션 실무자는 결과가 현장에서 타당한지, 머신러닝 엔지니어는 성능·지연·안정성이 운영 기준을 만족하는지 확인한다.

### 리포트나 서비스로 연결할 때

패션 MD·마케터는 결과를 의사결정과 캠페인에 적용하고, 분석가는 리포트와 대시보드로 근거를 전달한다. 데이터 엔지니어는 데이터를 정기적으로 갱신한다. 데이터 과학자는 모델과 실험 결과의 의미를 설명하며, 머신러닝 엔지니어는 배포·감시·되돌리기를 책임진다.

> **역할 지도의 읽는 법**<br>
> 데이터 분석가가 질문을 이해하지 않아도 된다는 뜻도, 패션 MD가 데이터 품질과 무관하다는 뜻도 아니다. 중요한 산출물은 각 단계 사이의 단순 인계가 아니라 공동 검토를 통해 완성된다.

작은 브랜드에서는 한 사람이 데이터 추출·정리·분석·리포트를 함께 맡기도 한다. 직무명만 보고 일을 단정하지 말고 **그 사람이 워크플로우의 어느 단계를 실제로 책임지는지** 확인해야 한다.

## 짧은 활동: 프로젝트 역할과 산출물 정하기

“첫 구매 후 30일 안에 재구매하는 고객의 비율을 높인다”는 프로젝트를 가정한다.

1. 비즈니스 질문과 성공 지표를 구체적으로 작성한다.
2. 내부에 있을 가능성이 높은 데이터와 새로 확보해야 할 데이터를 구분한다.
3. 각 워크플로우 단계의 산출물을 하나씩 정한다.
4. 패션 MD·데이터 분석가·데이터 엔지니어가 공동 검토해야 할 지점을 표시한다.
5. 결과를 리포트로 먼저 검증할지 서비스에 연결할지 이유와 함께 선택한다.

## 이 장의 핵심

- 데이터 확보는 내부 DB·플랫폼·파일·외부 자료·조사·실험 등 질문과 상황에 따라 달라진다.
- 먼저 비즈니스 질문과 기존 데이터 상태를 확인한 뒤 필요한 데이터만 추가로 확보한다.
- 프로젝트는 질문·점검·확보·통합·정제·분석·해석을 거쳐 리포트 또는 서비스로 이어진다.
- 리포트는 사람이 판단하고, 서비스는 시스템이 반복 실행하므로 운영·감시·중단 절차가 더 필요하다.
- 데이터 직무와 패션 실무자는 한 워크플로우에서 책임이 다르지만 중요한 단계는 공동으로 검토한다.
