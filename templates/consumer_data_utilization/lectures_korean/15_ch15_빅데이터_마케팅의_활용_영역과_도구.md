# 분석을 의사결정으로 연결하기: 패션 커머스의 6가지 활용 영역과 도구 선택

이상치 탐지, RFM, 이미지 유사도, SEO, UX 실험과 생성형 AI는 그 자체로 사업 목표가 아니다. 어떤 상품을 만들고, 얼마에 팔고, 누구에게 무엇을 보여주며, 얼마나 준비할지 결정할 때 가치를 만든다.

이 장에서는 지금까지 배운 방법을 상품기획·가격·검색·개인화·재고·UX라는 여섯 의사결정 영역에 연결한다. 특정 업체를 암기하는 대신 **결정→필요 데이터→방법→행동→성과·위험**을 먼저 정의하고 플랫폼과 노코드 도구를 고른다.

## 생각해 보기: 추천 화면 뒤에 무엇이 필요한가?

쇼핑 앱에서 ‘이 원피스와 함께 본 재킷’, ‘재고 3개’, ‘회원 전용 가격’이 한 화면에 보인다.

- 각 문구는 어떤 데이터를 사용했을까?
- 정확하지 않으면 고객과 사업에 어떤 피해가 생길까?
- 자동 추천을 도입하기 전에 사람이 정해야 할 것은 무엇일까?

> **중심 질문**
> 데이터와 도구를 어떤 의사결정을 위해 선택하고, 효과·비용·위험을 어떻게 함께 검증할까?

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- 패션 커머스의 여섯 데이터 활용 영역을 의사결정 질문으로 설명할 수 있다.
- 데이터 분석을 행동과 성과 검증까지 이어지는 폐루프로 설계할 수 있다.
- 기업 공식 자료가 공개한 사실과 공개하지 않은 세부를 구분할 수 있다.
- 이커머스 플랫폼과 노코드 도구를 요구사항·통합·비용·거버넌스로 비교할 수 있다.
- 하나의 사업 문제에 대한 도구선정 RFP를 작성할 수 있다.

## 핵심 용어

- **의사결정 루프(decision loop)**: 목표를 정의하고 데이터를 분석해 행동한 뒤 결과를 측정해 다음 판단에 반영하는 반복 과정.
- **다이나믹 프라이싱(dynamic pricing)**: 수요·재고·시간·경쟁·고객 규칙 등 정해진 입력에 따라 가격을 조정하는 전략. 반드시 실시간·개인별 자동 가격을 뜻하지 않는다.
- **노코드(no-code) 도구**: 코드를 직접 작성하는 양을 줄여 수집·분석·자동화를 설정하도록 돕는 소프트웨어. 데이터 설계와 검증이 사라지는 것은 아니다.
- **총소유비용(TCO)**: 구독료뿐 아니라 구축, 연동, 교육, 운영, 데이터 이동과 종료 비용을 포함한 전체 비용.
- **이탈 가능성(exit portability)**: 서비스를 바꾸거나 종료할 때 원자료·설정·결과를 표준 형식으로 내보낼 수 있는 정도.

## 1. 여섯 영역을 ‘도구’가 아니라 ‘결정’으로 본다

### 상품기획

“어떤 상품·색·사이즈를 시험할까?”를 결정한다. 검색·판매·반품·리뷰와 정성 조사에 워드카운트, 텍스트·이미지 분석을 적용해 소량 샘플이나 옵션 구성을 정할 수 있다. 판매율만 보지 말고 반품과 선택지의 다양성을 가드레일로 함께 본다.

### 가격

“어느 시점에 얼마로 제안할까?”를 결정한다. 원가·재고·수요·프로모션·경쟁 데이터를 기술통계, 예측과 실험으로 검토해 할인폭과 기간을 조정한다. 마진과 판매율뿐 아니라 고객 신뢰와 공정성도 확인한다.

### 검색

“어떤 페이지가 어떤 검색 의도에 답할까?”를 결정한다. 검색어·상품정보·노출·클릭을 SEO와 키워드 분석으로 검토해 카테고리와 상품정보를 개선한다. 유입과 구매가 늘어도 고객 오인이나 반품이 증가하지 않는지 확인한다.

### 개인화

“누구에게 어떤 상품이나 메시지를 어떤 순서로 보여줄까?”를 결정한다. 행동·구매·상품 속성·재고에 RFM, 유사도와 추천 방법을 적용할 수 있다. 전환과 상품 발견을 보되 노출 편향과 메시지 피로를 함께 감시한다.

### 재고

“상품과 옵션을 얼마나 준비할까?”를 결정한다. 판매·리드타임·반품·품절·날씨를 시계열, 이상치와 수요 예측으로 분석해 발주·재배치·재입고에 반영한다. 품절과 재고회전뿐 아니라 폐기와 현금 점유 비용을 본다.

### UX

“고객 여정의 어느 마찰을 먼저 개선할까?”를 결정한다. 퍼널·오류·정성 조사·실험 데이터에 퍼널, 코호트와 A/B 테스트를 적용해 필터·사이즈 안내·결제를 개선한다. 완료율과 함께 접근성 저하나 문의 증가가 없는지 확인한다.

한 분석이 여러 결정에 쓰일 수 있다. 리뷰의 ‘팔이 짧다’는 의견은 상품기획, 사이즈 안내 UX, 추천, 반품 예측에 모두 연결된다. 반대로 같은 ‘구매율’이라도 가격 실험과 검색 개선에서는 비교군과 해석이 다르다.

> **즉시 해석**
> 데이터 활용 영역을 나열하는 것은 시작일 뿐이다. 누가 언제 어떤 행동을 바꿀 것인지 정하지 않으면 대시보드가 늘어도 의사결정은 달라지지 않는다.

### 예: ‘77사이즈 하객 원피스’ 수요가 보인다

1. 검색어와 고객 문의에서 관련 표현이 늘었다.
2. 이것은 수요 **가설**이지 바로 대량생산할 근거는 아니다.
3. 기존 상품의 사이즈별 조회·품절·반품과 인터뷰를 함께 본다.
4. 소량 옵션이나 예약판매로 되돌릴 수 있는 파일럿을 설계한다.
5. 판매율뿐 아니라 핏 관련 반품·문의·마진을 함께 측정한다.
6. 결과를 다음 상품의 패턴·사이즈 구성에 반영한다.

이 루프에는 사람의 책임이 남는다. 분석가는 데이터 품질과 불확실성을 설명하고, 상품 담당자는 제작 가능성과 브랜드 방향을 판단하며, 법무·개인정보 담당자는 수집과 자동화의 허용 범위를 검토한다.

## 3. 여섯 영역의 핵심 위험을 함께 본다

### 상품기획: 검색량은 고객 요구의 일부다

검색량이 많은데 상품 수가 적은 ‘공백’은 아이디어 후보가 될 수 있다. 그러나 검색량이 구매 의사, 수익성, 제작 가능성과 같지는 않다. 품절 때문에 검색이 늘었는지, 정보만 찾는지, 기존 상품이 불만족스러운지 질적 근거와 소규모 실험으로 확인한다.

### 가격: 자동화보다 목적과 제약이 먼저다

| 가격 목표 | 함께 볼 지표 | 제약·위험 |
|---|---|---|
| 재고 소진 | 판매율, 잔여 재고, 리드타임 | 과도한 할인 학습, 브랜드 가치 |
| 마진 보호 | 주문당 이익, 쿠폰 비용 | 전환 감소, 고객 이탈 |
| 수요 대응 | 시간·채널별 수요 | 개인별 차별 우려, 설명 가능성 |
| 신규 고객 획득 | 첫 구매율, 재구매 | 기존 고객 불공정 인식 |

다이나믹 프라이싱을 ‘경쟁사보다 즉시 100원 낮추기’로만 이해하지 않는다. 변경 주기, 최저·최고 가격, 제외 대상, 승인 권한, 고객 고지, 오류 시 복구를 정책으로 정해야 한다.

### 개인화: 관련성과 발견의 균형

개인화는 익숙한 취향의 클릭을 높일 수 있지만, 계속 비슷한 상품만 보여주면 새로운 디자이너·스타일을 발견할 기회를 줄이고 노출 편향을 강화할 수 있다. 클릭률 외에 카탈로그 다양성, 신규 브랜드 노출, 반복 메시지 피로, 장기 리텐션을 본다.

### 재고: 예측 오차의 비용은 대칭이 아니다

한 벌 부족하면 품절 기회손실이 생기고, 한 벌 많으면 보관·할인·폐기 비용이 생긴다. 평균 오차만 낮추는 대신 상품 수명, 리드타임과 과소·과대 예측의 서로 다른 비용을 반영한다.

### 검색과 UX: 앞 장의 관찰·인과 원칙을 유지한다

SEO 노출 증가와 UX 전환 증가는 가격·재고·광고의 동시 변화와 섞일 수 있다. 변경 기록, 비교 기준과 가드레일을 남기고 가능한 경우 통제 실험을 사용한다.

## 4. 기업 사례는 공식 자료가 말한 범위까지만 사용한다

### Stitch Fix 사례

공식 자료에서는 고객·상품 데이터를 이용한 매칭, 추천과 재고 관련 알고리즘, 스타일리스트와 기술의 결합을 확인할 수 있다. 여기서 모든 추천 규칙, 현재 운영 수치나 개별 결정이 완전히 자동화되었다고 확대 해석해서는 안 된다. 이 사례의 강의 포인트는 사람과 모델이 역할을 나누는 방식이다.

### Inditex 사례

공식 연차보고서에서는 통합된 매장·온라인 운영과 디지털화·기술·물류에 관한 공개 내용을 확인할 수 있다. 이를 근거로 ‘완전 실시간 운영’, 정확한 재입고 주기나 공개되지 않은 데이터 파이프라인까지 단정하지 않는다. 이 사례는 공개된 사실과 반복되는 업계 통념을 분리해 읽는 연습에 적합하다.

Stitch Fix의 [Algorithms Tour](https://algorithms-tour.stitchfix.com/)는 협업 필터링, 스타일 매칭과 재고 관련 문제를 교육적으로 설명한다. 공식 연차보고서에서는 사업 모델과 사람·기술의 역할을 시점별로 확인할 수 있다.

Inditex 사례도 [공식 연차보고서](https://annualreport.inditex.com/anrpxxvui/en/download-centre)에 공개된 운영·기술 내용을 기준으로 삼는다. ‘Zara는 판매 데이터를 본사에 실시간 전송해 자동 생산한다’처럼 출처가 생략된 성공담은 실제 시스템의 사람, 주기, 예외와 한계를 지운다.

> **사례 읽기 규칙**
> 공식 문서가 ‘데이터를 활용한다’고 설명해도 데이터 필드, 모델, 정확도, 인과 성과가 모두 공개된 것은 아니다. **확인된 사실 / 기업의 주장 / 우리의 추론 / 공개되지 않음**을 네 칸으로 나누어 기록한다.

## 5. 플랫폼은 브랜드 순위가 아니라 요구사항으로 비교한다

네이버 스마트스토어, 카페24, 아임웹, Shopify는 대상 시장과 구축 방식이 다르고 기능도 계속 바뀐다. ‘국내 1위’, ‘디자인 자유도 최고’, ‘글로벌에 무조건 유리’ 같은 문장을 고정 지식으로 외우기보다 공식 문서로 아래 요구사항을 확인한다.

| 요구사항 | 확인 질문 | 공식 근거란 |
|---|---|---|
| 데이터 소유·내보내기 | 주문·고객·상품·이벤트 원자료를 어떤 형식으로 내보낼 수 있는가? |  |
| 이벤트 측정 | 상품조회·장바구니·결제 이벤트를 어떻게 수집·검증하는가? |  |
| API·연동 | 외부 분석·CRM·재고 도구와 어떤 방식으로 연결되는가? |  |
| 상품 구조 | 옵션·세트·다국어·다중통화를 지원하는가? |  |
| 동의·권한 | 쿠키 동의, 직원 권한, 삭제 요청을 어떻게 처리하는가? |  |
| 실험 | 기본 기능 또는 외부 도구로 안전한 실험이 가능한가? |  |
| 운영 지원 | 장애 대응, 교육, 파트너 생태계는 필요한 수준인가? |  |
| 총소유비용 | 구독·결제·앱·개발·교육·이전·종료 비용은 얼마인가? |  |

플랫폼의 기본 통계가 질문에 충분할 수 있다. 더 많은 도구를 붙이는 것이 목표가 아니라, 필요한 결정에 비해 현재 근거가 부족할 때만 추가한다.

| 통합·저장 | 채널 데이터 연결, 대시보드 집계 | 고객·주문 ID 규칙, 중복·결측 처리 |
| 분석 | 퍼널·코호트·리포트 계산 | 질문·비교군·해석 한계 설정 |
| 활성화 | CRM 메시지, 추천, 리뷰 노출 | 대상·빈도·금지 조건·승인 설정 |
| 실험 | 변형 배정, 지표 집계 | 가설·표본·가드레일·중단 판단 |
| 거버넌스 | 권한·로그·삭제 기능 | 법적 역할, 보유기간, 책임자 결정 |

기존에 살펴본 크리마리뷰, 라플라스, Bigin, 씨그로, 아이템스카우트, 판다랭크, GA4와 Amplitude는 **제품 이름**이 아니라 이 기능 층을 이해하기 위한 후보 예시로 다룬다. 실제 기능·가격·지원 플랫폼은 사용 시점의 공식 문서에서 확인한다.

> **참고 자료로 읽기**
> 위 제품명과 플랫폼 목록은 암기하거나 고정 순위를 만드는 학습 내용이 아니다. 핵심 평가는 데이터 내보내기, 권한, 통합, 비용, 평가와 종료 가능성이다. 제품 사례는 매 학기 공식 문서의 확인일을 기록해 갱신한다.

> **문제 발생**
> ‘클릭 몇 번이면 연동’이 되더라도 잘못 정의한 `purchase` 이벤트, 중복 고객 ID, 누락된 환불, 동의 없는 광고 대상은 자동으로 고쳐지지 않는다. 노코드는 코딩 부담을 줄일 수 있지만 데이터 책임을 없애지 않는다.

## 실습: 하나의 결정에 대한 도구선정 RFP

자주 쓰는 쇼핑 앱을 관찰해 여섯 영역 중 하나를 고른다. 화면 기능을 칭찬하는 데서 끝내지 말고 다음 표를 채운다.

| 항목 | 작성 |
|---|---|
| 개선할 고객·사업 결정 |  |
| 현재 근거와 부족한 근거 |  |
| 필요한 최소 데이터 |  |
| 반드시 필요한 기능 3개 |  |
| 있으면 좋은 기능 |  |
| 후보: 기존 플랫폼 기능 |  |

| 공식 문서에서 확인한 근거·확인일 |  |

### 선택 문장

> “도구 A가 유명해서”가 아니라 “결정 ___에 필요한 데이터 ___와 기능 ___을 공식 문서에서 확인했고, 기존 도구로는 ___이 부족하다. ___주 파일럿에서 ___과 ___을 측정하며, ___이면 중단한다”라고 쓴다.

## 이 장의 핵심

- 데이터 활용은 상품기획·가격·검색·개인화·재고·UX라는 결정 영역으로 연결된다.
- 분석은 목표→근거→사람의 판단→행동→성과·가드레일→학습의 폐루프로 설계한다.
- 검색량, 클릭률과 예측값은 행동 가설을 돕지만 수요·인과·수익성을 자동으로 증명하지 않는다.
- 기업 사례는 공식 공개 사실과 기업 주장, 우리의 추론, 비공개 세부를 구분한다.
- 플랫폼과 노코드 도구는 브랜드 평판보다 데이터 소유, 기능, 연동, 거버넌스, TCO와 이탈 가능성으로 비교한다.
- 노코드는 코딩 부담을 줄일 수 있지만 이벤트 설계, 품질, 해석, 동의와 책임을 대신하지 않는다.

## 학습할 점

1. 도구보다 먼저 어떤 의사결정을 개선할지 정했는가?
2. 분석 결과가 어떤 행동으로 이어지고 누가 승인하는가?
3. 주 성과와 고객·수익·공정성 가드레일을 함께 보는가?
4. 기업 사례에서 공개 사실과 추론을 분리했는가?
5. 구축부터 종료까지 데이터와 비용을 통제할 수 있는가?

## 학습 점검

1. 패션 커머스의 여섯 데이터 활용 영역을 쓰시오.
2. 검색량이 높은 카테고리를 바로 대량생산하면 안 되는 이유는 무엇인가?
3. 다이나믹 프라이싱이 반드시 실시간·개인별 자동 가격을 뜻하지 않는 이유를 설명하시오.
4. 기업 공식 사례를 읽을 때 네 칸으로 구분할 것은 무엇인가?
5. 노코드 도구를 사용해도 사람이 해야 하는 데이터 업무를 세 가지 쓰시오.
6. 플랫폼 비교에서 월 구독료 외에 확인할 TCO 항목을 두 가지 쓰시오.

## 알아볼 것: 생성형 AI로 도구를 고를 때

1. RFP 표를 제공하고 빠진 요구사항과 반대 의견을 요청한다.
2. 후보 도구의 기능·가격 비교를 만들게 한 뒤 모든 셀에 공식 문서 URL과 확인일을 직접 채운다.
3. ‘이 도구를 도입하지 않고 현재 플랫폼으로 해결하는 방법’도 함께 요청해 불필요한 구매를 줄인다.

> **알아두기**
> 플랫폼과 도구의 기능·가격·정책은 자주 바뀌며 생성형 AI가 오래된 요금제나 마케팅 문구를 사실처럼 말할 수 있다. 계약 전 공식 문서, 실제 데모, 데이터 내보내기와 종료 조건을 확인한다.
