# 패션 데이터의 흐름: 운영 기록에서 의사결정과 서비스까지

패션 기업은 데이터 분석을 하지 않아도 매일 데이터를 만든다. 고객이 가입하면 고객 정보가, 상품을 등록하면 상품 정보가, 주문이 들어오면 판매·재고·배송 정보가 생긴다. 고객이 상품을 사지 않더라도 검색하고 클릭하고 장바구니에 담는 과정이 기록될 수 있다. 리뷰와 상품 이미지도 데이터다.

이 데이터는 대부분 **분석을 위해 일부러 만든 데이터가 아니다.** 쇼핑몰과 브랜드가 상품을 팔고 배송하고 반품을 처리하려면 반드시 필요한 운영 기록이다. 분석가는 이렇게 이미 쌓인 기록을 찾아 연결하고, 비즈니스 질문에 답할 수 있는 데이터로 바꾼다.

> **이 장의 중심 질문**<br>
> 패션 기업의 일상적인 운영 기록은 어떻게 분석 가능한 데이터가 되고, 발견된 패턴은 어떻게 의사결정이나 서비스로 이어질까?

## 학습 목표

이 단원을 마치면 다음을 설명할 수 있다.

- 패션 산업에서 분석 목적과 무관하게 데이터가 계속 생성되는 이유
- 고객 DB·상품 DB·판매 DB가 서로 다른 정보를 담는 이유와 Key를 이용한 연결
- 같은 패션 데이터를 Table·JSON·Network로 다르게 표현하는 이유
- 회사 안팎의 데이터를 상황에 맞게 수집하고, 없던 데이터는 실험으로 만드는 방법
- Business Question에서 Report 또는 Service까지 이어지는 분석 Workflow
- Data Engineer·Data Analyst·Data Scientist·ML Engineer와 패션 실무자의 역할 차이

> **읽기 안내**
> 이 장은 길다. 핵심은 1~4·7절(데이터가 생기는 이유 → Business Question과 Data Audit → 세 가지 기본 DB와 JOIN → 전체 Workflow)이다. 5절(Table·JSON·Network)은 3장에서, 6절(수집 다섯 상황)은 5장에서 더 자세히 다루므로 처음에는 훑고 지나가도 된다.

## 1. 패션 산업은 운영하면서 데이터를 만든다

쇼핑몰에서 고객이 코트 한 벌을 구매하는 장면만 보아도 여러 시스템이 동시에 움직인다.

- 고객 DB는 누가 구매했는지 기록한다.
- 상품 DB는 어떤 색상·핏·가격의 상품인지 기록한다.
- 주문·판매 DB는 누가 무엇을 언제 몇 개 샀는지 기록한다.
- 재고 DB는 판매 후 남은 수량을 바꾼다.
- 배송 시스템은 주소와 배송 상태를 기록한다.
- 반품 시스템은 반품 이유와 회수 상태를 기록한다.
- 웹사이트는 검색·클릭·장바구니 같은 행동을 기록할 수 있다.
- 상품 페이지와 리뷰에는 텍스트·이미지가 쌓인다.

이처럼 패션 산업은 이미 구축된 데이터를 다시 분석에 활용하기 좋은 산업이다. 물론 데이터가 존재한다고 곧바로 분석할 수 있다는 뜻은 아니다. 저장 위치와 형식이 다르고, 연결 기준이 없거나 품질이 낮을 수도 있다. 그러나 처음부터 모든 데이터를 새로 만들 필요가 없다는 점은 큰 장점이다.

### 물리적 의류에서 디지털 의류와 이미지까지

앞으로는 기존의 고객·상품·판매 데이터에 새로운 유형이 더해질 가능성이 높다. 예를 들면 3D 의복 데이터, 3D Body Scan, 3D Garment Mapping, Digital Twin, Virtual Try-on 이미지, AI 생성 상품 이미지·패션 디자인, 영상 기반 착장 데이터, 가상 패션 콘텐츠다.

이것을 “모든 패션 기업이 곧 3D 기업이 된다”는 식으로 과장할 필요는 없다. 핵심은 상품과 콘텐츠가 물리적 의류에서 디지털 의류·이미지까지 확장되면서 **저장하고 연결하고 분석할 데이터 유형이 더 다양해진다**는 점이다.

## 2. 데이터 직무는 패턴을 찾고 활용하는 일이다

데이터 직무의 공통 목적은 운영 기록에서 의미 있는 패턴을 찾고, 그 패턴이 실제 행동으로 이어지게 만드는 것이다.

예를 들어 A 쇼핑몰의 판매 데이터를 분석해 다음 패턴을 발견했다고 하자.

> **강남 지역에 거주하는 30대 남성 직장인은 20~25만 원대의 남색 오버사이즈 코트를 많이 구매한다.**

같은 분석 결과라도 활용 방법은 두 가지로 나뉜다.

### 패턴을 리포트로 활용

사람이 분석 결과를 읽고 판단한다. 상품기획팀은 다음 시즌 코트 구성과 가격대를 검토하고, 마케팅팀은 광고 타깃과 메시지, 프로모션을 기획한다.

### 패턴을 서비스로 활용

분석 결과가 시스템 안의 기능으로 작동한다. 시스템이 같은 조건의 신규 고객을 찾고, 추천 상품을 고른 뒤, 매일 오전 9시에 남색 오버사이즈 코트 추천 이메일을 자동 발송할 수 있다.

## 3. 먼저 Business Question과 Data Audit

분석 프로젝트의 첫 질문은 “어떤 데이터를 가져올까?”보다 **“무엇을 알고 싶은가?”**에 가깝다.

예를 들어 “매출을 높이자”는 범위가 너무 넓다. “최근 3개월 동안 첫 구매 고객의 30일 이내 재구매율이 낮아진 이유는 무엇인가?”처럼 대상·기간·행동을 구체화해야 필요한 데이터도 정할 수 있다. 이것이 **Business Question**이다.

질문을 정한 다음에는 곧바로 외부 데이터를 모으지 않고, 회사가 이미 가진 데이터를 점검한다. 이를 **Data Audit(데이터 감사)**이라고 한다.

### 1) 데이터가 존재하는가?

고객 DB, 상품 DB, 주문·반품 기록, 장바구니 기록, 클릭 로그가 실제로 저장되는지 확인한다. 화면에 보이는 정보라도 과거 이력이 저장되지 않으면 분석에 사용할 수 없다.

### 2) 어디에 저장되어 있는가?

쇼핑몰 관리자 화면, Cafe24·Shopify 같은 플랫폼, ERP, CRM, Excel·CSV, 사내 DB, Google Analytics, 광고 플랫폼 등 위치를 찾는다. 같은 “판매 데이터”라도 주문 시스템과 회계 시스템에 서로 다른 기준으로 저장될 수 있다.

### 3) 어떤 형태인가?

Excel, CSV, SQL Database, JSON, API Response, 로그 파일, 이미지, 영상 등 저장 형태를 확인한다. 형태에 따라 읽는 도구와 정리 방법이 달라진다.

### 4) 서로 연결할 수 있는가?

데이터를 많이 모으는 것보다 **서로 다른 데이터를 연결할 Key가 있는가**가 중요하다. 고객 DB와 판매 DB가 모두 같은 `customer_id`를 사용해야 “이 고객이 무엇을 샀는가?”를 알 수 있다.

## 4. 패션 쇼핑몰의 세 가지 기본 DB

처음 데이터베이스를 접한다면 DB를 “특정 업무의 기록을 모은 표”라고 이해해도 좋다. 다음은 가상 패션 쇼핑몰의 가장 기본적인 세 표다.

### 고객 특성 DB: 누가 구매했는가?

| customer_id | age_group | gender | region | occupation |
| --- | --- | --- | --- | --- |
| C102 | 30s | Male | Gangnam | Office Worker |
| C315 | 20s | Female | Bundang | Student |
| C411 | 40s | Female | Mapo | Office Worker |

### 상품 특징 DB: 무엇을 구매했는가?

| product_id | category | color | fit | price |
| --- | --- | --- | --- | ---: |
| P501 | Coat | Navy | Oversized | 229000 |
| P320 | Shirt | White | Regular | 69000 |
| P711 | Jacket | Black | Slim | 189000 |

### 판매 DB: 누가 무엇을 언제 구매했는가?

| order_id | customer_id | product_id | qty | purchase_date |
| --- | --- | --- | ---: | --- |
| O9001 | C102 | P501 | 1 | 2026-08-01 |
| O9002 | C315 | P320 | 2 | 2026-08-02 |
| O9003 | C102 | P501 | 1 | 2026-08-10 |

세 표는 각각 필요한 정보만 담는다. 판매 DB에 고객의 직업과 상품의 색상을 매번 다시 적지 않으므로 중복을 줄이고, 고객이나 상품 정보가 바뀔 때 한 곳만 수정할 수 있다.

### JOIN: 공통 번호로 표 연결하기

**JOIN(조인)**은 서로 다른 표를 공통된 번호로 연결하는 작업이다. SQL 문법보다 먼저 연결 원리를 이해해야 한다.

- 판매 DB의 `customer_id=C102`를 고객 DB에서 찾으면 “30대·남성·강남·직장인”을 알 수 있다.
- 판매 DB의 `product_id=P501`을 상품 DB에서 찾으면 “Navy·Oversized·Coat·229,000원”을 알 수 있다.
- 두 연결을 합치면 “C102 고객이 어떤 특성의 상품을 구매했는가?”를 분석할 수 있다.

```text

```

중요한 것은 표가 세 개라는 사실이 아니라, **각 표가 다른 질문에 답하고 공통 Key로 연결될 때 새로운 분석 질문에 답할 수 있다**는 점이다.

## 5. 모든 데이터가 Excel 모양은 아니다

고객·상품·판매 DB처럼 행(Row)과 열(Column)이 분명한 데이터는 가장 익숙하다. 그러나 데이터는 목적에 따라 저장 모양이 달라진다.

### Table / Relational Data

행은 한 건의 기록, 열은 기록의 속성을 나타낸다. 상품별 판매량 합계, 고객별 구매 횟수처럼 정렬·필터·집계하고 정확하게 연결해야 하는 데이터에 알맞다.

### JSON: 정보 안에 또 다른 정보 담기

장바구니에는 한 고객 아래 여러 상품이 있고, 각 상품마다 사이즈·색상·수량 같은 옵션이 달린다. 이처럼 정보 안에 목록이나 다른 정보가 포함될 때 JSON 같은 계층 구조가 편리할 수 있다.

```json
{
  "customer_id": "C102",
  "cart": [
    {
      "product_id": "P501",
      "product_name": "Oversized Coat",
      "color": "Navy",
      "size": "L",
      "qty": 1
    },
    {
      "product_id": "P320",
      "product_name": "Basic Shirt",
      "color": "White",
      "size": "L",
      "qty": 2
    }
  ]
}
```

JSON 문법을 외우는 것이 목적은 아니다. 한 고객이 여러 상품과 옵션을 동시에 가진다는 구조를 그대로 중첩해 표현할 수 있다는 점만 이해하면 된다. 필요하면 JSON도 나중에 행과 열로 펼쳐 분석할 수 있다.

### Network / Graph Data: 관계 자체를 저장하기

고객과 상품, 상품과 브랜드, 상품과 카테고리처럼 **무엇이 무엇과 연결되었는가**가 중요하다면 Network 또는 Graph 형태로 표현할 수 있다.

```text
[C102]
  │
  ├── 구매 ── [P501 Coat] ── 소속 ── [Brand A]
  │
  └── 관심 ── [P711 Jacket] ── 분류 ── [Outerwear]
```

## 6. 데이터를 실제로 가져오는 다섯 가지 상황

데이터 구조를 이해했다면 이제 필요한 데이터를 어디서 어떻게 가져올지 정한다. 현실의 수집은 한 가지 도구로 끝나지 않는다.

### Case 1. 회사 내부에 이미 존재하는 데이터

주문 DB, 고객 DB, 상품 DB, ERP, CRM, 재고 DB, 클릭 로그를 먼저 확인한다. 이미 운영 중인 데이터는 새로 조사하는 것보다 추가 구축 비용이 적고, 실제 업무 행동과 직접 연결되어 있다는 장점이 있다.

다만 존재 여부만으로 충분하지 않다. 분석 기간이 보존되는지, ID가 일관적인지, 개인정보 이용 범위가 적절한지 함께 확인한다.

### Case 2. 쇼핑몰 플랫폼에 있는 데이터

Cafe24나 Shopify 같은 플랫폼의 관리자 화면에서 주문 데이터를 CSV로 내려받을 수 있고, 반복 업무라면 API로 자동 수집할 수도 있다.

**API(Application Programming Interface)**는 다른 시스템에 정해진 형식으로 요청하고 응답받는 창구다. 비전공자라면 식당의 주문 창구처럼 생각해도 좋다.

> 쇼핑몰 시스템에 “지난 일주일의 주문 정보를 보내줘”라고 약속된 형식으로 요청하면, 시스템이 주문 결과를 정해진 형식으로 돌려주는 창구가 API다.

API가 있다고 모든 데이터에 자동 접근할 수 있는 것은 아니다. 제공 항목, 권한, 호출 횟수, 보안 정책을 확인해야 한다.

### Case 3. API를 사용할 수 없는 경우

현실에서는 Excel·CSV, 이메일 첨부, 보안 USB, 사내 공유폴더로 데이터를 전달받기도 한다. 이것이 반드시 구식이거나 잘못된 방식은 아니다. 기업 규모, 기존 시스템, 협력사 관계, 보안 정책에 따라 전달 방식은 다양하다.

이 경우 파일 버전, 기준 날짜, 컬럼 의미, 누가 만든 파일인지 기록하지 않으면 나중에 같은 분석을 재현하기 어렵다.

### Case 4. 회사 밖에 있는 외부 데이터

경쟁사 상품·가격, 날씨, 트렌드, SNS, 검색 결과처럼 내부 DB에 없는 정보는 Open API, 공개 데이터, 크롤링, 외부 데이터 구매로 확보할 수 있다.

**크롤링(crawling)**은 웹페이지의 정보를 프로그램으로 읽어 필요한 항목을 모으는 방법이다. 기술적으로 읽을 수 있다고 무조건 수집해도 되는 것은 아니다. 사이트 이용약관, 저작권, 개인정보, 접근 제한과 수집 목적을 먼저 확인해야 한다.

### Case 5. 아직 존재하지 않는 데이터

“할인 배너를 빨간색으로 바꾸면 구매율이 증가하는가?”라는 질문은 기존 주문 DB만으로 답하기 어렵다. 빨간 배너를 본 고객의 결과가 아직 없기 때문이다. 이때는 필요한 데이터를 실험으로 새로 만든다.

**A/B Test**는 비슷한 고객을 두 그룹으로 나누어 한 가지 조건만 다르게 보여주고 결과를 비교하는 방법이다.

## 7. Fashion Data Workflow

실제 분석 업무는 다음 흐름으로 이해할 수 있다.

### 1. Business Question

비즈니스에서 무엇을 결정하기 위해 어떤 질문에 답해야 하는지 정한다.

### 2. Data Audit

회사에 어떤 데이터가 존재하고 어디에 저장되어 있으며, 분석 가능한 기간·품질·권한인지 점검한다.

### 3. Data Collection

내부 DB, 플랫폼, 파일, API, 외부 데이터, 실험 중 적절한 방법으로 필요한 데이터를 확보한다.

### 4. Data Integration

`customer_id`, `product_id`, 날짜 같은 Key로 고객·상품·판매 데이터를 연결한다.

### 5. Data Cleaning

누락된 값, 중복 주문, 잘못된 가격, 서로 다른 날짜 형식, `Navy`와 `navy`처럼 표기가 다른 값을 정리한다. 분석 시간의 상당 부분이 이 단계에 쓰일 수 있다.

### 6. Analysis

집계·비교·시각화·통계·예측 모델 등을 이용해 반복되는 패턴과 차이를 찾는다. 도구보다 Business Question에 맞는 방법을 고르는 것이 중요하다.

### 7. Interpretation

패턴이 왜 생겼는지, 우연이나 데이터 오류는 아닌지, 실제 상품기획·마케팅에서 어떤 의미가 있는지 판단한다. “강남 30대 남성의 코트 구매 비중이 높다”는 결과만으로 그 집단 전체가 코트를 좋아한다고 단정해서는 안 된다. 고객 수, 노출된 상품, 캠페인과 계절도 함께 봐야 한다.

### 8-A. Report 또는 8-B. Service

사람이 판단할 수 있도록 리포트와 대시보드로 전달하거나, 추천·CRM·재고·마케팅 자동화 시스템이 사용할 수 있도록 서비스에 연결한다.

이 흐름은 한 번만 지나가는 직선이 아니다. 분석 중 `occupation` 값이 대부분 비어 있음을 발견하면 Data Audit이나 Collection으로 돌아가야 한다. 서비스 성과가 낮으면 Business Question과 Metric을 다시 정의할 수도 있다. **되돌아가는 것은 실패가 아니라 현실적인 분석 과정**이다.

## 8. Workflow 안에서 일하는 사람들

데이터 직무는 서로 완전히 분리된 섬이 아니다. 같은 Workflow의 다른 구간에 더 많은 책임을 갖는다.

| Role | Primary Workflow Responsibility | Fashion E-commerce Example |
| --- | --- | --- |
| Data Engineer | Collection · Storage · Integration · Pipeline | Loads order and click logs daily and maintains customer IDs |
| Data Analyst | Audit · Cleaning · Exploration · Dashboard · Report | Summarizes coat buyers and reports differences by region and age |
| Data Scientist | Statistics · Prediction · Segmentation · Recommendation | Segments customers and estimates coat purchase or recommendation scores |
| ML Engineer | Model Operations · Service · Monitoring | Connects the recommendation model to the store and keeps it reliable |
| Fashion MD / Marketer | Business Question · Interpretation · Decision | Applies findings to assortment, pricing, targeting, and promotions |

아래 표는 직무를 고정된 상자로 나누는 조직도가 아니라, 하나의 프로젝트에서 **누가 어떤 단계에 더 큰 책임을 갖는지** 보여주는 역할 지도다. 회사 규모와 프로젝트 성격에 따라 책임은 겹칠 수 있다.

| Workflow Stage | Fashion MD / Marketer | Data Analyst | Data Engineer | Data Scientist | ML Engineer |
|---|---|---|---|---|---|
| Question · Metric | 요구 정의·성과 기준 합의 | 측정 가능성 검토 | 데이터 존재 여부 확인 | 모델 목표·평가 설계 | 운영 제약 확인 |
| Audit · Collection | 업무 맥락 설명 | 품질·누락 점검 | 수집·저장·식별자 설계 | 라벨·표본 편향 점검 | 실시간 입력 조건 점검 |
| Integration · Cleaning | 용어·업무 규칙 확인 | 분석용 표 작성 | 파이프라인·JOIN 운영 | 학습 데이터 구성 | 학습·서빙 데이터 일치 확인 |
| Analysis · Validation | 결과의 현업 타당성 검토 | 집계·비교·시각화 | 재현 가능한 데이터 제공 | 통계·예측·실험 | 성능·지연·안정성 검증 |
| Report · Service | 의사결정·캠페인 실행 | 리포트·대시보드 | 정기 갱신 | 모델·실험 해석 | 배포·모니터링·롤백 |

> **역할 지도의 읽는 법**
> `Data Analyst`가 질문을 이해하지 않아도 된다는 뜻도, `Fashion MD`가 데이터 품질과 무관하다는 뜻도 아니다. 중요한 산출물은 각 단계 사이의 인계가 아니라 공동 검토를 통해 완성된다.

큰 기업에서는 역할이 세분화될 수 있지만, 작은 브랜드에서는 한 사람이 데이터 추출·정리·분석·리포트를 함께 맡기도 한다. 직무명만 보고 일을 단정하지 말고 **그 사람이 Workflow의 어느 단계를 실제로 책임지는지** 확인해야 한다.

## 짧은 활동: 우리 쇼핑몰의 Data Audit

가상의 패션 쇼핑몰에서 “첫 구매 후 30일 안에 재구매하는 고객의 특징은 무엇인가?”를 분석한다고 하자. 다음 질문에 답해 보자.

1. 반드시 필요한 DB와 컬럼은 무엇인가?
2. 고객 DB와 판매 DB를 연결할 Key는 무엇인가?
3. 재구매를 계산하려면 어느 정도 기간의 판매 기록이 필요한가?
4. `customer_id`가 없는 비회원 주문은 어떻게 처리할 것인가?
5. 분석 결과는 리포트와 서비스 중 어디에 활용할 수 있는가?

## 이 장의 핵심

- 패션 기업은 분석을 하지 않아도 고객·상품·주문·재고·행동·이미지 데이터를 운영 과정에서 계속 만든다.
- 분석의 시작은 무조건 새 데이터를 모으는 일이 아니라 Business Question을 정하고 기존 데이터를 점검하는 Data Audit이다.
- 고객 DB는 누가, 상품 DB는 무엇을, 판매 DB는 누가 무엇을 언제 구매했는지를 기록한다.
- `customer_id`와 `product_id` 같은 Key로 표를 JOIN하면 고객 특성과 상품 특성을 구매 기록에 연결할 수 있다.
- 데이터는 Table뿐 아니라 중첩 정보를 담는 JSON, 관계를 강조하는 Network 등 여러 구조로 존재한다.
- 수집은 내부 DB, 플랫폼·API, 파일, 외부 데이터뿐 아니라 A/B Test로 필요한 데이터를 만드는 일도 포함한다.
- 분석 결과는 사람이 읽는 Report가 되거나 추천·CRM·자동화 Service의 일부가 될 수 있다.
- 3D 의복·Body Scan·AI 이미지·Virtual Try-on은 기존 데이터를 없애는 것이 아니라 새로운 데이터 유형을 더한다.
- 데이터 직무들은 하나의 Workflow에서 서로 다른 구간을 주로 담당하며, 회사 규모에 따라 한 사람이 여러 역할을 수행할 수 있다.

## 학습 점검

1. 패션 기업에서 분석 목적 없이도 데이터가 생성되는 사례를 다섯 가지 쓰시오.
2. 고객 DB·상품 DB·판매 DB가 각각 답하는 질문은 무엇인가?
3. JOIN을 SQL 문법 없이 `customer_id`와 `product_id`를 사용해 설명하시오.
4. 장바구니 데이터를 JSON으로 표현하면 편리한 이유는 무엇인가?
5. Table과 Network가 같은 고객·상품 데이터를 다르게 표현하는 이유는 무엇인가?
6. API·파일·크롤링·A/B Test가 필요한 상황을 하나씩 제시하시오.
7. 패턴을 Report로 활용하는 경우와 Service로 활용하는 경우의 차이를 설명하시오.
8. Data Analyst와 ML Engineer가 Workflow에서 주로 담당하는 부분은 어떻게 다른가?

<details>
<summary>정답과 해설 보기</summary>

1. 고객 가입, 상품 등록, 주문, 재고 변경, 배송, 반품, 검색, 클릭, 장바구니, 리뷰, 이미지 등록 등에서 다섯 가지를 들 수 있다.
2. 고객 DB는 “누가?”, 상품 DB는 “무엇을?”, 판매 DB는 “누가 무엇을 언제 몇 개 구매했는가?”에 답한다.
3. 판매 DB의 `customer_id`를 고객 DB의 같은 번호와 연결하고, 판매 DB의 `product_id`를 상품 DB의 같은 번호와 연결하는 작업이다.
4. 한 고객 아래 여러 상품이 있고 각 상품에 사이즈·색상·수량 같은 옵션이 포함되는 중첩 구조를 자연스럽게 표현할 수 있기 때문이다.
5. Table은 정확한 값의 집계와 Key 연결에, Network는 고객·상품·브랜드 사이의 연결을 따라가는 질문에 더 적합하기 때문이다.
6. 플랫폼의 반복 주문 수집에는 API, 협력사의 단발성 자료에는 파일, 내부에 없는 공개 웹 정보에는 적법성을 확인한 크롤링, 아직 존재하지 않는 조건의 효과에는 A/B Test를 사용할 수 있다.
7. Report는 사람이 결과를 읽고 판단하며, Service는 분석 결과가 추천·CRM·자동화 기능 안에서 직접 작동한다.
8. Data Analyst는 주로 Audit·Cleaning·탐색·Dashboard·Report를 담당하고, ML Engineer는 모델이나 분석 로직을 실제 Service에 안정적으로 연결하고 운영한다.
