# Prompt Analysis and Evaluation

## 학습 목표

생성형 AI를 분석 업무에 사용할 때 프롬프트는 멋진 문장을 쓰는 기술이 아니라 **분석 과업을 검증 가능한 명세로 바꾸는 도구**다. 이 장은 프롬프트를 Application의 개별 기능이 아니라 Analysis의 질문 정의·통제·평가 문제로 다룬다.

이 장을 마치면 다음을 할 수 있다.

- 분석 질문을 목표·입력·제약·출력·평가 기준으로 구조화한다.
- zero-shot·one-shot·few-shot을 예시 수의 차이로 구분한다.
- 프롬프트 비교에서 모델·버전·seed·입력 자료를 통제한다.
- 형식 준수와 내용 정확성을 별도로 평가한다.
- 작은 평가셋과 사람의 승인 절차로 분석 결과를 검증한다.

## 1. 프롬프트는 분석 설계서다

“리뷰를 분석해 줘”는 범위가 너무 넓다. 긍정·부정을 나눌 것인지, 사이즈·소재·배송 주제를 찾을 것인지, 어떤 결정에 쓸 것인지 알 수 없다. 좋은 프롬프트는 다음 여섯 요소를 연결한다.

| 요소 | 확인할 질문 | 패션 리뷰 분석 예시 |
|---|---|---|
| Goal | 어떤 결정을 돕는가? | 다음 생산분의 사이즈 안내 수정 |
| Evidence | 어떤 자료만 근거로 쓰는가? | 승인된 상품 리뷰 500건 |
| Task | 어떤 분석을 수행하는가? | 리뷰별 주제와 불만 강도 분류 |
| Constraints | 무엇을 추측하면 안 되는가? | 리뷰에 없는 신체 정보 추정 금지 |
| Output | 어떤 구조로 반환하는가? | JSON: review_id, topic, evidence |
| Evaluation | 무엇이면 통과하는가? | 라벨 정확도, 근거 인용, 누락률 |

```text
목표: 사이즈 안내 수정 후보를 찾는다.
입력: 제공된 리뷰만 사용한다.
과업: 각 리뷰를 size, material, delivery, other 중 하나로 분류한다.
제약: 리뷰에 없는 원인을 만들지 않는다.
출력: review_id, topic, evidence를 가진 JSON 배열.
평가: evidence는 입력 문장의 짧은 구절이어야 한다.
```

이 구조는 AI가 정답을 보장하지 않는다. 다만 무엇을 시켰고 어떤 기준으로 실패를 판단할지 명확하게 만든다.

## 2. 예시 수와 과업 수행 방식

- **Zero-shot**: 설명과 출력 규칙만 제공한다.
- **One-shot**: 올바른 입력·출력 예시 하나를 함께 준다.
- **Few-shot**: 정상·경계·예외 사례를 몇 개 제공한다.

few-shot이 항상 더 정확한 것은 아니다. 잘못된 예시는 오류를 반복시키고, 예시가 한 카테고리에 치우치면 다른 카테고리를 놓칠 수 있다. 예시는 “많이”보다 **판단 경계를 보여주도록** 고른다.

## 3. 비교 실험에서 바꿀 것은 하나다

프롬프트 A와 B를 비교하면서 모델 버전, 입력 리뷰, 생성 설정까지 동시에 바꾸면 무엇이 결과를 개선했는지 알 수 없다. 분석 실험처럼 비교 조건을 통제한다.

| 고정할 조건 | 이유 |
|---|---|
| 모델과 버전 | 모델 변화와 프롬프트 효과를 분리한다 |
| 입력 데이터와 순서 | 쉬운 표본·어려운 표본 차이를 막는다 |
| temperature·seed 등 설정 | 무작위 변동을 줄인다 |
| 출력 스키마 | 형식 차이 때문에 평가가 달라지지 않게 한다 |
| 평가자와 루브릭 | 평가 기준의 이동을 막는다 |

한 번의 보기 좋은 결과로 결론 내리지 않는다. 정상 사례, 애매한 사례, 틀리면 위험한 사례를 포함한 작은 평가셋을 만들고 여러 조건에서 반복한다.

## 4. 형식과 내용은 별도로 평가한다

유효한 JSON이라고 분석이 맞는 것은 아니다. 다음 네 층을 나누어 본다.

1. **형식 평가**: JSON 파싱, 필수 필드, 허용 라벨.
2. **내용 평가**: 정답 라벨과의 Precision·Recall·F1.
3. **근거 평가**: 입력에 없는 사실을 만들지 않았는가?
4. **업무 평가**: 실제 상품기획 결정에 도움이 되는가?

예를 들어 `topic="size"`라는 JSON이 정상이어도 실제 리뷰가 배송 지연에 관한 것이라면 내용 오류다. 라벨이 맞더라도 근거 문장이 입력에 없다면 환각이다. 정확해도 이미 알고 있는 내용을 반복한다면 업무 가치는 낮다.

## 5. 사람의 책임과 기록

분석용 생성형 AI 작업에는 최소한 다음을 기록한다.

- 모델과 버전
- 프롬프트 버전
- 입력 데이터의 범위와 날짜
- 예시와 검색 자료
- 생성 설정
- 자동 평가 결과와 실패 사례
- 최종 검토자와 승인일

민감한 고객 데이터는 외부 모델에 그대로 전송하지 않는다. 이용 계약, 보관 정책, 비식별화와 접근 권한을 먼저 확인한다. AI 출력은 분석 후보이며 가격·재고·고객 차별 같은 중요한 결정은 담당자가 근거를 검토한 뒤 승인한다.

<div class="lesson-section-box lesson-activity-box"><strong>짧은 활동</strong></div>

상품 리뷰 20개를 골라 모호한 프롬프트 A와 여섯 요소를 갖춘 프롬프트 B를 만든다. 같은 입력·모델·설정으로 실행하고 형식 준수율, 주제 정확도, 근거 없는 문장 수를 비교한다. 결과가 좋아진 사례뿐 아니라 두 프롬프트가 모두 틀린 사례도 기록한다.

<div class="lesson-section-box lesson-summary-box"><strong>이 장의 핵심</strong></div>

- 프롬프트는 분석 과업의 목표·근거·제약·출력·평가를 연결하는 명세다.
- zero/one/few-shot은 예시 수와 구성의 차이이며 성능 향상을 보장하지 않는다.
- 프롬프트 비교에서도 다른 조건을 고정하고 여러 사례로 반복해야 한다.
- 형식 준수, 내용 정확성, 근거 충실성, 업무 가치를 따로 평가한다.
- 모델·프롬프트·입력·설정·평가·승인 이력을 남겨야 결과를 재현할 수 있다.

## 학습 점검

1. 긴 프롬프트와 검증 가능한 작업 명세의 차이는 무엇인가?
2. few-shot 예시에 경계 사례가 필요한 이유는 무엇인가?
3. JSON이 유효해도 분석 결과가 틀릴 수 있는 이유는 무엇인가?
4. 프롬프트 A/B 비교에서 고정해야 할 조건을 세 가지 쓰시오.
5. 고객 리뷰 분석 결과에서 사람이 최종 승인해야 할 판단을 하나 제시하시오.
