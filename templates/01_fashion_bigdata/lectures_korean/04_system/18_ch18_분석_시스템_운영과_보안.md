# Operating and Securing an Analytics System

## 학습 목표

앞 장에서 견적을 만들어 시스템을 도입했다면 이제 그것을 **매일 돌리는** 문제가 남는다. 이 장은 서버 설치나 보안 장비 설정이 아니라, 분석가가 **운영 중인 시스템에서 지켜야 할 규칙과 읽어야 할 지표**를 다룬다.

이 장을 마치면 다음을 할 수 있다.

- 노트 파일, 실행 중인 Kernel의 변수, 결과 파일이 서로 다른 상태임을 설명하고 재현 가능한 실행 조건을 기록한다.
- 대화형 작업을 Batch 작업으로 바꿀 때 필요한 주기·실패 처리·중복 방지·복구 규칙을 설계한다.
- "느리다"를 latency·throughput·utilization·idle resource 같은 지표로 바꿔 병목을 찾는다.
- 표준화·자동화·캐싱·자원 배정·이동 최소화·유휴자원 감소로 같은 품질을 더 적은 비용으로 반복 생산한다.
- 데이터 민감도에 맞는 최소 사용, 인증과 최소 권한, 비밀정보 분리, 암호화와 데이터 위치를 적용한다.
- 사본·백업·삭제·로그·사고 대응의 기준을 세우고 키 노출 시 대응 순서를 설명한다.

> **시스템 파트의 구성**  
> 16장은 데이터가 *어디에 있고 어떻게 이동하는지*를, 17장은 시스템을 *도입하기 전에 비용을 어떻게 산정하는지*를, 이 장은 도입한 시스템을 *어떻게 운영하고 지키는지*를 다룬다.

> **이 장의 판단 기준**  
> 데이터 분석에는 자원·시간·인력·도구 비용이 발생한다. 분석가는 정확도뿐 아니라 **요구 품질을 충족하는 범위에서 처리시간과 총비용도 함께 관리**해야 한다.

## 1. 운영의 기본 단위: Process·Runtime·Notebook Kernel

Python 파일이나 노트북을 실행하면 운영체제는 실행 중인 프로그램 단위인 **Process**를 만든다. Jupyter·Colab에서는 **Kernel 또는 Runtime**이 코드 셀을 실행하고 변수와 데이터를 RAM에 유지한다.

다음 상태는 서로 다르다.

- **노트 저장**: 코드와 설명이 `.ipynb` 파일에 남는다.
- **변수 존재**: 실행 중인 Kernel의 RAM에만 값이 있다.
- **결과 파일 저장**: CSV·PNG·모델이 Storage에 기록된다.
- **Runtime 종료**: RAM의 변수와 일부 임시 파일이 사라진다.

노트북을 저장했다고 메모리의 DataFrame까지 영구 보관된 것은 아니다. 16장의 사다리로 말하면 변수는 메모리 층에, 노트 파일과 결과는 스토리지 층에 있다. Kernel을 다시 시작하고 위에서부터 실행해도 같은 결과가 나오도록 입력 위치, 패키지 버전, 실행 순서와 난수 설정을 기록한다.

## 2. 대화형 작업과 Batch 작업

**대화형 작업**은 코드를 실행하고 바로 결과를 확인하며 다음 질문을 정하는 방식이다. 표본 확인, 그래프 조정과 오류 탐색에 적합하다.

**Batch 작업**은 정해진 입력과 규칙에 따라 예약 시간이나 조건에 맞춰 실행한다. 매일 판매 집계, 주간 고객군 계산과 이미지 임베딩 갱신에 적합하다.

대화형 분석을 Batch로 바꿀 때는 다음을 추가한다.

- 실행 주기와 기준 시간대
- 입력 지연이나 누락 처리
- 성공·실패·처리 행 수 기록
- 같은 날짜 재실행 시 중복 방지
- 오류 알림과 검수 담당자
- 중간 저장과 복구 방법

16장에서 본 YAML 설정 파일은 이 항목들(기간·경로·주기·임곗값)을 코드 밖에 두는 방법이다. 자동화는 사람의 반복 시간을 줄이지만 잘못된 규칙도 반복한다. 검증과 중단 조건까지 포함해야 비용 효율화가 된다.

## 3. 성능과 비용을 읽는 지표

### Latency: 한 결과가 완성되는 시간

- **개념**: 요청부터 결과가 준비될 때까지 걸린 시간이다.
- **패션 사례**: 재고 보고서가 대기 8분, 데이터 이동 5분, 계산 7분, 검증 10분 뒤 완성된다.
- **비용·효율성**: 계산만 줄이기보다 가장 긴 대기나 재작업을 먼저 줄인다.

\[
\text{전체 Latency} = \text{대기} + \text{이동} + \text{처리} + \text{검증} + \text{재작업}
\]

### Throughput: 일정 시간에 완료하는 양

- **개념**: 초당 행 수, 분당 이미지 수, 하루 완료 보고서 수다.
- **패션 사례**: 분당 이미지 200장의 임베딩을 만들면 300만 장의 순수 처리에 약 250시간이 필요하다.
- **비용·효율성**: 한 장의 속도가 빨라도 전체 마감에 늦으면 Batch 크기와 병렬성을 검토한다.

### Cost-performance: 비용당 검증된 결과

- **개념**: 같은 품질을 만족하는 결과 한 단위를 만드는 비용이다.
- **패션 사례**: GPU가 네 배 빠르지만 전체 비용이 여섯 배라면 작은 작업에서는 CPU가 더 경제적일 수 있다.
- **비용·효율성**: 서로 다른 품질의 결과를 가격만으로 비교하지 않는다.

\[
\text{검증된 결과당 비용} = \frac{\text{자원·도구·사람을 포함한 총비용}}{\text{검증을 통과한 결과 수}}
\]

### Energy efficiency: 에너지당 완료량

- **개념**: `이미지/kWh`처럼 에너지 한 단위로 끝낸 작업량이다.
- **패션 사례**: 같은 품질과 마감을 만족하는 이미지 처리 환경의 실행 시간과 전력 사용을 비교한다.
- **비용·효율성**: 측정값이 없으면 임의의 친환경 수치를 만들지 않고 자원 크기·실행 시간·완료량을 기록한다.

### Resource utilization: 할당 자원의 활용 정도

- **개념**: CPU·GPU·RAM 가운데 실제로 사용된 비율과 시간 패턴이다.
- **패션 사례**: GPU는 쉬는데 CPU가 이미지를 준비하느라 바쁘면 GPU 추가보다 입력 파이프라인을 점검한다.
- **비용·효율성**: 평균 사용률만 높이지 말고 최대 메모리·대기·실패율을 함께 본다.

### Idle resource: 비용은 들지만 일하지 않는 자원

- **개념**: 켜져 있지만 유효한 계산을 하지 않는 서버·GPU·DB 시간이다.
- **패션 사례**: 2시간 작업이 끝난 GPU Notebook이 주말 내내 실행된다.
- **비용·효율성**: 자동 종료와 예약 실행을 사용한다. 복구용 예비 자원은 목적을 명시해 단순 낭비와 구분한다.

### 알아두면 좋은 원칙: Amdahl의 법칙

**Amdahl의 법칙**은 작업 일부를 매우 빠르게 만들어도 개선되지 않은 나머지 단계가 전체 속도 향상의 한계를 정한다는 결과다. 전체 시간 중 병렬화되지 않는 비율을 \(s\), 병렬 부분의 속도 향상을 \(p\)라 하면 단순화한 전체 향상은 다음처럼 생각할 수 있다.

\[
\text{전체 속도 향상} = \frac{1}{s + \frac{1-s}{p}}
\]

상품 이미지 처리에서 파일 읽기·전처리·검증이 30%, GPU 추론이 70%라면 추론 장치를 아무리 빠르게 해도 전체 속도는 이론적으로 약 \(1/0.3=3.33\)배를 넘기 어렵다. GPU를 추가하기 전에 각 단계의 시간을 나눠 측정해야 하는 이유다.

## 4. 병목을 찾는 순서

| 관찰 | 먼저 확인할 대상 | 가능한 접근 |
|---|---|---|
| 파일을 여는 데 오래 걸림 | Storage·Network | 필요한 컬럼만 읽기, 형식 점검 |
| `merge` 중 메모리 오류 | RAM·중간 사본 | Key 중복·컬럼·dtype 확인 |
| CPU 사용률이 계속 높음 | 계산량·알고리즘 | 벡터 연산·집계 단순화 검토 |
| CPU·GPU 사용률 모두 낮음 | 입력 대기·코드 흐름 | 파일 읽기·Network·작업 순서 확인 |
| GPU 메모리 오류 | VRAM·Batch 크기 | Batch·해상도·모델 크기 조정 |
| DB 조회가 느림 | 조건·스캔량·운영 부하 | 기간·컬럼 축소, 분석 DB 확인 |

측정 없이 장비를 키우면 병목은 그대로인데 비용만 커질 수 있다. 작업을 입력 읽기, 정제, 계산, 저장과 검증으로 나누고 각 단계의 시간·메모리·자원 사용을 기록한다.

## 5. 사례: 상품 이미지 임베딩 배치

상품 이미지 300만 장에서 512차원 임베딩을 만든다고 가정한다.

1. 표본 1천 장으로 파일 손상과 모델 입출력을 CPU에서 확인한다.
2. 이미지 하나의 크기와 Batch별 RAM·VRAM을 측정한다.
3. CPU와 GPU에서 데이터 준비를 포함한 latency와 throughput을 비교한다.
4. GPU 사용률이 낮다면 이미지 읽기·해제·전송이 병목인지 확인한다.
5. 실패 시 처음부터 다시 하지 않도록 완료된 상품 ID와 중간 결과를 저장한다.
6. 요구 품질을 만족한 결과 수를 기준으로 시간과 비용을 비교한다.

GPU가 가장 빠르다는 사실만으로 선택하지 않는다. 전처리·전송·검증과 재실행까지 포함한 전체 처리시간과 비용을 본다.

## 6. 품질을 유지하며 분석 비용 효율화하기

비용 효율화는 가장 싼 도구를 고르거나 정확도를 무조건 낮추는 작업이 아니다. 먼저 필요한 품질, 완료 시한, 처리량과 보안 조건을 정한 뒤 같은 조건을 만족하는 방법의 total cost를 비교한다. 변경 전후에는 **품질·latency·throughput·사람 시간·오류율·검증된 산출물당 비용**을 같은 데이터로 측정한다.

### 공통 분석의 표준화

- **개념**: 반복되는 지표 정의, 입력 컬럼, 제외 규칙, SQL·Python 코드와 검증 절차를 재사용 가능한 형태로 정리한다.
- **분석 사례**: 부서마다 다르게 계산하던 순매출을 `결제액−취소−환불`로 정의하고 공통 쿼리와 품질 점검을 사용한다.
- **비용·효율성 시사점**: 정의 회의와 코드 중복, 결과 불일치에 따른 재작업을 줄인다. 모든 질문을 한 템플릿에 억지로 맞추지 않고 예외 조건과 버전을 기록한다.

### 검증된 반복 작업의 자동화

- **개념**: 사람이 매번 같은 순서로 수행하는 수집·정제·집계·배포를 일정과 규칙에 따라 실행한다.
- **분석 사례**: 매주 월요일 반품률을 계산하고 행 수·결측률이 기준을 벗어나면 배포를 멈춘 뒤 담당자에게 알린다.
- **비용·효율성 시사점**: 반복 작업시간과 누락을 줄이지만, 잘못된 규칙도 빠르게 반복할 수 있다. 입력 검증, 로그, 승인 단계, 중단·재실행과 되돌리기를 자동화 비용에 포함한다.

### 중간 결과의 캐싱

- **개념**: 계산 비용이 큰 동일 결과를 다시 사용할 수 있도록 일정 기간 저장한다.
- **분석 사례**: 변하지 않은 상품 이미지의 512차원 임베딩을 매 분석마다 다시 계산하지 않고 모델·이미지 버전과 함께 보관한다.
- **비용·효율성 시사점**: GPU 시간과 latency를 줄이는 대신 저장비와 오래된 결과를 쓸 위험이 생긴다. 원본·코드·모델이 바뀌었을 때 캐시를 무효화하는 조건과 만료일을 정한다.

### 작업에 맞는 도구와 자원 배정

- **개념**: 작은 표 탐색, 대규모 집계, 이미지 모델처럼 작업 특성에 맞춰 로컬 CPU·DB·분산 처리·GPU를 나눈다.
- **분석 사례**: 주문 필터와 상품별 집계는 데이터가 있는 DB에서 수행하고, 집계된 작은 표만 노트북으로 가져와 그래프를 만든다. 이미지 임베딩에만 GPU를 사용한다.
- **비용·효율성 시사점**: 모든 단계를 가장 큰 장비에 올리는 비용을 피한다. 작은 대표 데이터로 실행 시간·메모리·스캔량을 측정한 뒤 필요한 단계만 확장한다.

### 데이터 이동 최소화

- **개념**: 원본 전체를 반복 복사하는 대신 데이터가 있는 곳에서 필터·집계하고 필요한 결과만 이동한다.
- **분석 사례**: 주문 5천만 건을 내려받는 대신 DB에서 월·카테고리별 반품률을 계산해 수백 행만 전달한다.
- **비용·효율성 시사점**: 네트워크 시간·전송비·로컬 저장비와 개인정보 사본을 줄인다. 원본과 계산 위치가 다른 이유가 있다면 지역·권한·도구 호환성을 함께 기록한다.

### 유휴자원 감소

- **개념**: 작업이 끝난 뒤 사용하지 않는 GPU·서버·개발 DB와 오래된 스냅샷을 찾아 줄인다.
- **분석 사례**: GPU 노트북에 자동 종료 시간을 설정하고, 야간 배치 시간에만 자원을 시작하며 프로젝트 종료 시 임시 디스크를 검토한다.
- **비용·효율성 시사점**: 사용하지 않는 시간의 비용을 줄인다. 서비스 복구에 필요한 예비 자원은 삭제 대상이 아니라 가용성 비용으로 명시한다.

### 최신 도구와 기술의 도입 판단

- **개념**: 새로운 DB·AI 모델·분산 도구를 지속적으로 파악하되, 기존 방법과 같은 요구조건에서 비교하는 작은 시험을 수행한다.
- **분석 사례**: 새 텍스트 모델을 기존 모델과 동일한 상품명 평가셋으로 비교하고 분류 품질, 처리시간, API 비용, 한글·기존 데이터 형식 호환성과 운영 가능성을 기록한다.
- **비용·효율성 시사점**: 최신이라는 이유만으로 교체하면 학습, 데이터 변환, 코드 수정, 병행 운영, 재검증과 되돌리기 비용이 생긴다. 다음 항목을 통과할 때만 확대한다.

1. 현재 도구보다 필요한 분석 품질을 안정적으로 높이거나 같은 품질을 더 낮은 총비용으로 제공하는가?
2. 개발뿐 아니라 검증·배치·장애 상황을 포함한 전체 처리시간이 개선되는가?
3. 저장 형식, API, 권한, 기존 코드와 보고 체계에 연결되는가?
4. 팀의 학습시간, 데이터·코드 이전, 이중 운영과 계약 종속 비용을 포함했는가?
5. 실패했을 때 기존 방식으로 되돌릴 수 있는가?

효율화의 결과는 단순 사용률 상승이 아니라 **요구 품질과 시한을 만족한 결과를 더 적은 총비용으로 반복 생산하는 상태**다.

## 7. 데이터 분류와 최소 사용

보안은 모든 데이터를 같은 방식으로 잠그는 작업보다 **데이터의 민감도와 사용 목적에 맞는 통제**에서 시작한다.

패션 기업의 데이터를 다음처럼 구분해 볼 수 있다.

| 예 | 주요 위험 | 기본 판단 |
|---|---|---|
| 공개 상품명·정가 | 무단 재사용, 오래된 정보 | 출처·갱신 시점 확인 |
| 출시 전 디자인·원가 | 영업기밀 노출 | 제한된 프로젝트 공간 |
| 고객 연락처·주소 | 개인정보 침해 | 목적·권한·보존 기간 제한 |
| 주문·반품·행동 로그 | 재식별과 프로파일링 | 가명화·최소 컬럼·접근 기록 |
| 결제 인증정보 | 높은 보안·규제 위험 | 분석 환경으로 직접 반입하지 않음 |

고객군별 반품률 계산에 이름과 전화번호가 필요하지 않다면 조회하지 않는다. 전체 기간보다 필요한 기간, 전체 고객보다 승인된 대상, 직접 식별자보다 가명 분석 ID를 사용한다. 데이터가 줄어들면 메모리와 비용뿐 아니라 노출 범위도 줄어든다.

## 8. 인증과 최소 권한

**인증**은 사용자가 누구인지 확인하고, **인가**는 그 사용자가 어떤 데이터와 기능을 사용할 수 있는지 정한다.

분석 환경의 기본 원칙은 다음과 같다.

- 개인별 계정을 사용하고 계정을 공유하지 않는다.
- 가능하면 다중 인증을 사용한다.
- 업무에 필요한 DB·테이블·컬럼·행만 조회하도록 권한을 제한한다.
- 분석가는 보통 운영 DB의 수정·삭제·관리자 권한을 사용하지 않는다.
- 개발·검증·운영 환경의 계정과 데이터를 구분한다.
- 부서 이동, 프로젝트 종료와 퇴사 시 권한을 회수한다.
- 일정 기간 사용하지 않은 계정과 과도한 권한을 정기 점검한다.

권한을 넓게 부여해 편의를 얻으면 실수와 계정 탈취의 영향 범위도 커진다. 필요한 작업이 바뀔 때는 영구적인 관리자 권한보다 승인된 일시 권한을 검토한다.

클라우드에서는 제공자와 조직이 보안 책임을 나누는 **공동 책임** 원칙이 적용된다. 제공자가 물리 장비와 기반 서비스를 지키더라도 테이블 권한, 개인정보 사용 목적, 잘못된 쿼리와 계정 관리는 사용하는 조직의 책임으로 남는다.

## 9. 비밀정보 관리

DB 비밀번호, API 키, 클라우드 접근 키, SSH 키와 인증서는 데이터가 아니라 시스템에 접근할 수 있는 **비밀정보**다. 다음 위치에 직접 적지 않는다.

- Python·SQL 코드와 Markdown 문서
- 공개 또는 팀 공유 Git 저장소
- 노트북 출력 셀과 오류 메시지
- 메신저와 이메일 본문
- 분석 결과 CSV와 그래프 메타데이터
- 16장의 YAML 같은 환경설정 파일

조직이 승인한 비밀관리 서비스나 환경 변수로 코드를 값과 분리한다.

```python
import os

db_password = os.environ["FASHION_DB_PASSWORD"]
```

환경 변수를 썼다는 사실만으로 관리가 끝나는 것은 아니다. 누가 값을 설정·조회할 수 있는지, 로그와 프로세스 정보에 노출되는지, 언제 교체되는지 확인한다.

키가 노출되었을 가능성이 있으면 다음 순서로 대응한다.

1. 해당 키를 비활성화하거나 폐기한다.
2. 필요한 경우 새 키를 발급하고 권한을 최소화한다.
3. 접근 로그에서 사용 흔적과 영향 범위를 확인한다.
4. 저장소 기록·노트북 출력·캐시 등 남은 사본을 처리한다.
5. 노출 경로와 재발 방지 규칙을 기록한다.

파일에서 문자열만 지워도 Git 기록이나 공유 사본에는 값이 남아 있을 수 있으므로 키 자체의 교체가 중요하다.

## 10. 전송·저장 암호화와 데이터 위치

데이터는 저장된 상태와 네트워크로 이동하는 상태 모두에서 보호해야 한다.

- DB와 서비스 연결은 조직이 승인한 암호화 연결을 사용한다.
- 노트북·서버·객체 스토리지의 저장 암호화와 키 관리 주체를 확인한다.
- 데이터가 저장·백업되는 국가와 지역을 확인한다.
- 개인 장치, 이동식 저장장치와 개인 클라우드 동기화를 제한한다.
- 이메일 첨부 대신 접근이 통제되고 만료 가능한 공유 방식을 사용한다.

암호화는 접근권한을 대신하지 않는다. 권한이 있는 사용자는 복호화된 데이터를 볼 수 있으므로 인증·인가·로그와 함께 사용한다.

## 11. 사본·백업·삭제와 복구

분석 과정에서는 원본 외에도 여러 사본이 생긴다.

- 다운로드한 CSV·Excel
- 노트북의 출력과 임시 파일
- 전처리된 중간 데이터
- 모델 학습용 캐시
- 그래프에 포함된 개별 데이터 라벨
- 스토리지 버전과 서버 스냅샷
- 자동 백업과 로그

각 사본에 대해 소유자, 저장 위치, 접근권한, 보존 기간과 삭제 방법을 정한다. 프로젝트 종료 시 실행 자원과 계정을 정리하고, 재현에 필요한 코드·쿼리·집계 결과만 정책에 따라 보존한다.

백업은 삭제의 반대가 아니라 복구를 위한 별도 통제다. 백업도 암호화와 권한 관리가 필요하며, 실제로 복원되는지 정기적으로 시험한다. 랜섬웨어나 실수로 원본과 온라인 백업이 함께 손상되는 상황도 고려한다.

## 12. 로그·탐지·대응·복구

분석 시스템은 "접근을 막는 것"뿐 아니라 예상과 다른 활동을 발견하고 대응할 수 있어야 한다.

로그에는 다음 정보가 도움이 된다.

- 사용자·서비스 계정과 접속 시각
- 조회한 DB·테이블과 실행한 작업
- 대량 다운로드와 권한 변경
- 배치 작업의 성공·실패·처리 행 수
- 모델·데이터·코드 버전
- 비용 급증과 비정상적인 자원 생성

민감한 원문 데이터와 비밀번호를 로그에 그대로 남기지 않는다. 로그 자체의 접근권한과 보존 기간도 관리한다.

사고 대응 절차에는 보고 담당자, 계정·키 차단, 영향 범위 확인, 데이터·서비스 복구, 관련자 통지와 재발 방지 검토가 포함된다. NIST Cybersecurity Framework 2.0의 **Govern·Identify·Protect·Detect·Respond·Recover**는 보안을 하나의 수명주기로 이해하는 데 사용할 수 있다.

## 13. 패션 AI 프로젝트의 운영·보안 사례

고객 행동 로그 2TB와 상품 이미지 300만 장으로 추천 임베딩을 만든다고 가정한다.

### 데이터 준비

- 행동 로그는 승인된 분석 저장소에 유지한다.
- 고객 직접 식별자는 제외하고 가명 ID와 필요한 Event만 사용한다.
- 상품 이미지는 사용권한과 보존 범위를 확인한다.

### 계산 환경

- SQL·CPU 환경에서 기간 필터, 중복 제거와 품질 점검을 수행한다.
- 작은 이미지 표본으로 입력·출력과 평가 코드를 검증한다.
- 전체 이미지 임베딩에 GPU가 유리한지 CPU 기준선과 비교한다.
- GPU VRAM에 맞춰 배치 크기를 정하고 실패 시 재시작 위치를 기록한다.

### 결과와 운영

- 개인별 추천 결과 대신 필요한 수준의 평가 집계만 공유한다.
- 모델·데이터·코드 버전과 실행 비용을 기록한다.
- 권한이 통제된 저장소에 결과를 보관한다.
- 프로젝트 종료 시 임시 이미지·캐시·GPU·비밀키와 일시 권한을 정리한다.

이 사례에서 좋은 환경은 GPU 수가 가장 많은 환경이 아니라 필요한 품질과 속도를 충족하면서 데이터 노출, 비용과 복구 책임을 통제하는 환경이다.

## 14. 운영 체크리스트

### 실행과 성능

- Kernel을 다시 시작해도 같은 결과가 나오도록 입력·버전·순서를 기록했는가?
- Batch 작업에 주기, 실패 처리, 중복 방지, 알림, 복구 방법이 있는가?
- latency를 대기·이동·처리·검증·재작업으로 나눠 측정했는가?
- CPU·GPU·메모리 사용률과 최대 메모리를 함께 봤는가?
- 실패한 작업을 처음부터 다시 하지 않도록 중간 저장 지점을 정했는가?

### 비용 효율화

- 표준화·자동화·캐싱으로 줄일 비용과 새로 생길 유지관리 비용을 함께 계산했는가?
- 작업 종료 뒤 남는 GPU·디스크·스냅샷·로그를 확인하고 자동 종료를 설정했는가?
- 예산 알림이 있는가?
- 새 도구의 호환성, 학습·전환·병행 운영과 되돌리기 비용을 검토했는가?

### 데이터와 보안

- 데이터 민감도, 사용 목적과 보존 기간을 기록했는가?
- 직접 식별정보를 제외하거나 가명화할 수 있는가?
- 개인 계정, 다중 인증과 최소 권한을 적용했는가?
- 비밀정보가 코드·출력·저장소·설정 파일에서 분리되었는가?
- 암호화, 로그, 백업·복구와 사고 보고 절차가 있는가?

<div class="lesson-section-box lesson-activity-box"><strong>짧은 활동</strong></div>

다음 두 작업의 운영 계획을 만든다.

- 공개 상품 CSV 5MB에서 카테고리별 평균 가격 계산
- 고객 행동 로그 2TB와 상품 이미지 300만 장으로 추천 모델 평가

각 작업에 대해 대화형·Batch 중 실행 방식, latency와 throughput의 측정 단위, 예상 병목과 확인 방법, 필요한 권한, 비밀정보의 위치, 생기는 사본과 보존·삭제 기준, 사고 발생 시 대응 담당자를 작성한다. 앞 장에서 만든 견적과 비교해 운영 중 어떤 비용이 추가로 드러나는지도 적는다.

<div class="lesson-section-box lesson-summary-box"><strong>이 장의 핵심</strong></div>

- 노트 파일, Kernel의 변수와 결과 파일은 서로 다른 상태다. 재현 가능하도록 입력·버전·순서를 기록한다.
- 대화형 작업은 탐색에, Batch는 검증된 반복 작업에 적합하며 Batch에는 실패·중복·복구 규칙이 필요하다.
- latency·throughput·cost-performance·energy efficiency·utilization·idle resource를 목적에 맞게 구분한다.
- Amdahl의 법칙은 개선하지 않은 단계가 전체 가속의 한계를 정함을 보여주므로 단계별 시간을 먼저 측정한다.
- 병목을 측정한 뒤 필요한 자원만 조정해야 품질과 총비용을 함께 관리할 수 있다.
- 반복 분석은 표준화·검증된 자동화·캐싱·적절한 자원 배정·데이터 이동 최소화·유휴자원 감소로 효율화한다.
- 최신 도구는 품질·전체 처리시간·총비용·호환성·학습과 전환 비용을 기존 방식과 비교한 뒤 도입한다.
- 보안은 데이터 분류·최소 사용·인증·최소 권한·비밀관리·암호화로 시작하고, 클라우드에서는 공동 책임의 조직 몫을 확인한다.
- 임시 사본과 백업에도 접근권한·보존·삭제·복구 기준이 필요하다.
- 로그와 사고 대응은 탐지·차단·영향 확인·복구·재발 방지까지 연결한다.

1. 노트북을 저장했는데 Kernel 재시작 후 변수가 사라지는 이유는 무엇인가?
2. Batch 작업에 로그·중복 방지·복구 규칙이 필요한 이유는 무엇인가?
3. latency와 throughput을 패션 분석 사례로 구분하시오.
4. CPU와 GPU 사용률이 모두 낮은데 느릴 때 먼저 확인할 항목은 무엇인가?
5. 표준화·자동화·캐싱이 각각 줄일 수 있는 비용과 새로 만들 수 있는 비용을 설명하시오.
6. 새로운 분석 도구를 도입하기 전에 비교할 기준을 다섯 가지 쓰시오.
7. 인증과 인가의 차이를 설명하시오.
8. API 키가 저장소에 노출되었을 때 필요한 대응 순서를 설명하시오.
9. 분석 프로젝트에서 생길 수 있는 데이터 사본을 네 가지 쓰시오.

9. 다운로드 CSV, 노트북 출력, 중간 데이터, 캐시, 스냅샷, 백업과 로그 등이 있다.

## 핵심 용어

- **Process**: 실행 중인 프로그램 한 단위. 확인: 어떤 작업이 자원을 쓰는지.
- **Kernel·Runtime**: 노트북의 코드를 실행하고 변수를 메모리에 유지하는 실행 환경. 확인: 종료 시 무엇이 사라지는지.
- **Batch 작업**: 정해진 입력과 규칙으로 예약 시간에 실행하는 작업. 확인: 주기, 실패 처리, 중복 방지.
- **Latency**: 요청부터 결과까지 한 작업에 걸린 시간. 확인: 대기·이동·계산·검증의 합.
- **Throughput**: 일정 시간 동안 완료한 처리량. 확인: 행/초, 이미지/분, 작업/일.
- **Utilization**: 할당한 자원이 실제로 사용되는 정도. 확인: CPU·GPU·메모리 사용 패턴.
- **Idle resource**: 켜져 있지만 일하지 않는 자원. 확인: 자동 종료, 예약 실행.
- **공동 책임**: 서비스 제공자와 이용 조직이 보안·운영 책임을 나누는 원칙. 확인: 제공 범위와 조직 담당 업무.
- **인증**: 사용자가 누구인지 확인하는 과정. 확인: 개인 계정, 다중 인증.
- **인가**: 인증된 사용자가 할 수 있는 일을 정하는 과정. 확인: 최소 권한, 읽기·수정·삭제.
- **비밀정보**: API 키·DB 비밀번호·인증서처럼 노출되면 안 되는 값. 확인: 저장 위치, 교체, 접근 로그.
