# Adopting an Analytics System and Estimating Cost

## 학습 목표

분석가는 "이 분석을 하려면 무엇이 필요하고 얼마가 드는가"라는 질문을 반복해서 받는다. 노트북으로 충분한지, GPU를 빌려야 하는지, 데이터 웨어하우스를 계약해야 하는지는 감으로 정할 수 없다. 이 장은 도입 결정에 필요한 **견적**을 만드는 순서를 다룬다.

CPU 명령어 구조, 캐시 결합 방식, 특정 클라우드의 화면이나 서버 설치 명령처럼 전공 수준의 내용은 제외한다. 패션 분석 업무의 자원과 비용을 설명하고 견적의 근거를 제시할 수 있는 수준에 집중한다.

이 장을 마치면 다음을 할 수 있다.

- 데이터량과 실행 패턴에서 저장 공간과 메모리(RAM·VRAM) 요구량을 추정한다.
- 작업의 성격에 따라 CPU와 GPU 중 먼저 시험할 환경을 고르고 측정으로 확인한다.
- 로컬 장비·사내 서버·클라우드의 비용 성격(구매·구축·사용량)을 비교한다.
- 클라우드 비용이 실행 시간 외에 어디서 생기는지 나열한다.
- 사람·데이터·계산·저장·DB·전송·검증·운영·보안을 포함한 총비용을 일회성과 반복 비용으로 나눠 산정한다.
- 총비용을 의사결정의 기대효과·위험과 비교해 예상 순가치로 도입 여부를 판단한다.

> **시스템 파트의 구성**  
> 16장은 데이터가 *어디에 있고 어떻게 이동하는지*를, 이 장은 시스템을 *도입하기 전에 비용을 어떻게 산정하는지*를, 18장은 도입한 시스템을 *어떻게 운영하고 지키는지*를 다룬다.

> **이 장의 판단 기준**  
> 데이터 분석에는 자원·시간·인력·도구 비용이 발생한다. 분석가는 정확도뿐 아니라 **요구 품질을 충족하는 범위에서 처리시간과 총비용도 함께 관리**해야 한다.

## 1. 견적은 데이터량과 실행 패턴에서 시작한다

기업이 크면 보통 동시 사용자와 통제가 늘어 운영 비용이 커지지만, 회사 크기만으로 견적을 정할 수는 없다. 작은 브랜드의 이미지 생성 프로젝트도 GPU 반복 실행과 대용량 원본 보관 때문에 비쌀 수 있고, 큰 기업의 소규모 표본 분석은 비교적 저렴할 수 있다. **기업 규모는 승인·연동·운영 복잡도를 가늠하는 변수이고, 데이터량과 실행 패턴은 직접 자원량을 계산하는 변수**다.

견적을 시작할 때 먼저 적는 항목은 16장에서 본 측정 목록과 같다.

- 현재 행 수·컬럼 수·파일 크기와 하루에 새로 생기는 양
- 보관 기간과 사본 수
- 동시에 조회하는 사람과 자동 작업의 수
- 결과가 필요한 시점: 몇 초, 몇 분, 다음 날
- 한 번 실행하는가, 매일·매주 반복하는가
- 민감한 데이터의 포함 여부

이 숫자가 없으면 아래의 모든 계산이 추정이 아니라 추측이 된다.

## 2. 데이터 크기에서 메모리 요구량으로

5장에서 shape의 원소 수에 dtype의 byte 수를 곱해 원시 배열의 최소 크기를 추정했다(예: 300만 개 × 512차원 × float32 ≈ 5.72GiB). 견적에서는 여기에 두 가지를 더한다.

### 저장 파일 크기와 실행 중 메모리는 다르다

저장된 4GB CSV가 실행 중에도 정확히 4GB만 쓰는 것은 아니다.

- pandas DataFrame은 인덱스와 문자열 표현 때문에 원본 CSV보다 메모리를 더 쓸 수 있다.
- 큰 `merge`에서는 두 원본 DataFrame, Key 정렬 정보와 결과 DataFrame이 한동안 **함께** 존재한다.
- 정렬·집계·모델 실행 중에는 원본과 결과가 동시에 존재해 최대 메모리가 원본의 2~3배가 될 수 있다.
- 반대로 JPEG처럼 압축된 파일은 저장 크기가 작아도 메모리에 풀면 픽셀 수만큼 커진다.

```python
import pandas as pd

df = pd.read_csv("orders.csv")
print(f"파일 크기 기준이 아닌 실제 메모리: {df.memory_usage(deep=True).sum() / 1024**2:.1f} MiB")
print(df.dtypes)
```

작은 표본으로 실제 메모리를 재고, 전체 행 수로 비례 확장한 뒤 중간 복사본 여유를 곱하는 것이 견적의 기본이다. 메모리 요구량을 줄이려면 필요한 기간·행·컬럼만 읽고, dtype을 줄이며(예: `float64`→`float32`, 범주형 문자열→`category`), DB에서 먼저 집계하거나 파일을 묶음으로 처리한다.

### GPU에는 별도의 메모리가 있다

GPU 전용 메모리인 **VRAM**은 일반 RAM과 구분된다. 모델과 이미지 배치가 VRAM보다 크면 시스템 RAM이 남아 있어도 실패한다. 이때 배치 크기, 입력 해상도, 모델 크기와 숫자 정밀도를 조정한다. 견적에는 RAM과 VRAM을 따로 적는다.

## 3. CPU가 맡는 분석 작업

CPU는 다양한 명령과 조건 분기를 처리하는 범용 장치다. 다음 작업은 보통 CPU로 시작한다.

- CSV·Excel·Parquet 읽기와 dtype 확인
- pandas 필터·정렬·집계·결합
- 문자열과 날짜 정제
- SQL 클라이언트 실행
- 통계 요약과 작은 회귀·분류 기준선
- 그래프 작성과 결과 파일 저장

CPU에 여러 Core가 있어도 모든 Python 코드가 자동으로 동시에 실행되는 것은 아니다. 사용하는 라이브러리와 작업이 병렬 처리를 지원해야 한다. CPU 사용률이 낮은데 작업이 느리다면 CPU 성능보다 파일·네트워크 대기 또는 메모리 부족이 원인일 수 있다.

### 패션 사례

상품명 10만 건에서 브랜드 표기와 색상 단어를 정리하는 작업은 조건과 문자열 처리가 많다. 먼저 CPU에서 실행 시간을 측정한다. 작은 작업을 GPU로 옮기면 데이터를 준비하고 전송하는 시간이 계산 이득보다 클 수 있다.

## 4. GPU와 VRAM이 맡는 분석 작업

GPU는 많은 값에 같은 형태의 계산을 반복하는 데 강점이 있다. 패션 분석에서는 다음 작업에서 효과를 검토한다.

- 수십만 장 이상의 상품 이미지 임베딩 생성
- 이미지 분류·세그멘테이션·생성 모델 학습
- 큰 행렬곱이 반복되는 딥러닝 추론
- GPU를 지원하는 라이브러리의 대규모 병렬 계산

GPU가 효과를 내려면 세 조건이 필요하다.

1. **연산 적합성**: 동시에 수행할 반복 계산이 충분하다.
2. **소프트웨어 지원**: 코드와 라이브러리가 GPU를 실제로 사용한다.
3. **충분한 규모**: 준비·전송 비용보다 계산 절감 효과가 크다.

## 5. CPU와 GPU를 고르는 기준

| 작업 | 먼저 시험할 환경 | 이유 |
|---|---|---|
| 상품 CSV 5MB 품질 확인 | 로컬 CPU | 데이터와 계산량이 작음 |
| 주문 5천만 건 월간 집계 | 데이터가 있는 DB·CPU | 이동 전에 필터·집계 가능 |
| 고객 1만 명 회귀 기준선 | CPU | GPU 준비비가 더 클 수 있음 |
| 이미지 300만 장 임베딩 | GPU 검토 | 같은 모델 계산을 대량 반복 |
| 큰 이미지 모델 미세조정 | GPU와 VRAM 검토 | 큰 행렬 계산과 메모리가 필요 |

선택은 장치 이름이 아니라 측정으로 확인한다. 대표 표본에서 다음을 같은 조건으로 비교한다.

- 결과 품질
- 데이터 준비와 저장을 포함한 전체 실행 시간
- 최대 RAM·VRAM 사용량
- 실패와 재실행 횟수
- 사람의 설정·검증 시간
- 실행 한 번과 월간 반복의 총비용

### 알아두면 좋은 원칙: Moore의 법칙과 견적

Gordon Moore는 1965년 집적회로에 들어가는 부품 수가 빠른 속도로 증가하는 산업 추세를 관찰하고 전망했다. 이후 **Moore의 법칙**은 반도체 집적도가 세대마다 크게 향상되는 경향을 설명하는 말이 되었다. 물리학의 불변 법칙이나 "컴퓨터 속도와 저장 용량이 일정한 주기로 반드시 두 배가 된다"는 보장은 아니다.

견적에 주는 시사점은 분명하다. 같은 예산으로 가능한 분석 규모가 시간이 지나며 커질 수는 있지만, **견적에는 현재 측정값과 현재 가격을 쓰고 미래의 가격 하락을 확정 사실처럼 넣지 않는다.** 장비가 좋아졌다는 이유만으로 비효율적인 데이터 이동·정제·검증 과정이 사라지지도 않는다.

## 6. 어디서 돌릴 것인가: 로컬 장비·사내 서버·클라우드

16장에서 서버의 소유 방식을 온프레미스와 클라우드로 나눴다. 견적에서는 분석가의 로컬 장비까지 세 선택지를 놓고 비용 성격을 비교한다. 어느 하나가 항상 우수한 것은 아니며, 데이터 민감도, 작업 기간, 필요한 자원의 변화, 조직의 운영 인력과 기존 시스템을 함께 본다.

### 로컬 장비

- **개념**: 분석가의 노트북이나 워크스테이션에서 저장과 계산을 수행한다.
- **분석 사례**: 공개 상품 CSV와 작은 표본으로 그래프와 코드를 점검한다.
- **비용 성격**: 별도 실행 요금이 없지만 장비 구매·교체·고장과 사람의 관리시간이 든다. 고객 원본과 출시 전 이미지를 저장할 수 있는지는 조직 규정을 먼저 확인한다.

### 사내 서버·자체 데이터센터(온프레미스)

- **개념**: 조직이 서버·스토리지·네트워크를 보유하거나 전용 공간에서 운영한다.
- **분석 사례**: 여러 부서가 공통 웨어하우스와 분석 서버를 사용한다.
- **비용 성격**: 장비 구매, 전력·냉각, 설치라는 **큰 초기 구축비**와 패치·장애 대응·교체주기를 조직이 부담한다. 사용하지 않는 시간에도 감가와 운영비가 발생한다.

### 클라우드

- **개념**: 필요한 계산·저장·DB를 네트워크로 요청하고 사용량이나 계약에 따라 비용을 지불한다.
- **분석 사례**: 시즌마다 증가하는 이미지 처리 기간에만 GPU를 사용한다.
- **비용 성격**: 초기비가 거의 없고 **월 정액·사용량 과금**이라 빠르게 시작하고 크기를 조절할 수 있지만, 자원 종료·전송·권한·지역을 관리하지 않으면 비용과 위험이 누적된다.

| 판단 항목 | 로컬 장비 | 사내 서버 | 클라우드 |
|---|---|---|---|
| 시작 속도 | 보유 장비면 빠름 | 구매·설치 시 오래 걸릴 수 있음 | 계정·권한 준비 뒤 빠르게 생성 가능 |
| 크기 변경 | 장비 한도 내 | 구매·증설 필요 | 비교적 유연하지만 비용 변화 |
| 비용 성격 | 구매·교체 중심 | 구축·운영 인력 중심 | 사용량·구독·전송 중심 |
| 운영 책임 | 사용자·조직 | 주로 조직 | 제공자와 조직이 나눔 |
| 적합한 예 | 작은 탐색·교육 | 안정적인 반복 공동 작업 | 변동이 큰 작업·일시적 대규모 계산 |

선택할 때는 구매비와 시간당 요금만 비교하지 않는다. 예상 사용 기간, 평균·최대 사용률, 운영 인력, 중단 위험, 데이터 이동, 보안 검토와 기존 도구 전환 비용을 포함한다. 자원을 꾸준히 100% 가까이 쓰는 작업은 장기적으로 보유가 싸고, 시즌에만 몰리는 작업은 빌리는 편이 싸다.

## 7. 클라우드의 자원 구성과 비용 구성

클라우드는 네트워크를 통해 공유된 계산·저장·서비스 자원을 필요할 때 요청하고 사용량을 측정하는 운영 방식이다. 분석 작업에서 자주 만나는 자원은 다음과 같다.

- **가상 머신**: 운영체제와 CPU·메모리·GPU를 비교적 자유롭게 구성한다. 켜 둔 시간만큼 요금이 나간다.
- **관리형 노트북**: 브라우저에서 노트북과 원격 런타임을 사용한다. 시작이 빠르지만 런타임 종료, 패키지 버전, 임시 디스크와 자원 한도가 서비스 정책에 따라 달라진다.
- **관리형 DB·데이터 웨어하우스**: SQL 조회, 권한, 백업과 확장을 제공한다. 저장량과 스캔량·처리 시간으로 과금한다.
- **객체 스토리지**: CSV·Parquet·이미지·모델 파일처럼 큰 객체를 보관한다. 저장량과 요청·전송량으로 과금한다.

클라우드 비용은 서버 사용 시간 하나로만 결정되지 않는다.

- CPU·메모리·GPU가 실행된 시간
- 디스크와 객체 스토리지의 저장 용량·보존 기간
- DB가 읽거나 처리한 데이터 양
- 지역이나 외부 네트워크로 전송한 데이터 양
- 스냅샷·로그·백업·이전 버전
- 관리형 서비스와 고가용성 구성

GPU 작업이 끝난 뒤 노트북 화면만 닫으면 실행 자원이 계속 남을 수 있다. 견적에는 "실행 시간"뿐 아니라 중지 뒤에도 과금되는 디스크·고정 주소·스냅샷을 포함하고, 예산 한도와 비용 알림을 설정하는 비용도 넣는다.

## 8. 분석 비용을 산정하는 기본식

분석 비용은 컴퓨터 가격이나 클라우드 청구서만으로 계산하지 않는다. 데이터를 이해하고 정제하는 사람의 시간, 권한 검토, 품질 오류로 인한 재작업과 결과를 운영하는 비용이 함께 들어간다. 이렇게 사용 기간 전체의 구축·운영·인력·위험 비용을 합친 것을 **총소유비용(TCO, total cost of ownership)**이라고 한다.

\[
\begin{aligned}
\text{예상 총비용} ={}& \text{인력의 작업·대기시간} + \text{데이터 수집·정제} \\
&+ \text{계산·저장·API} + \text{DB 조회·전송} \\
&+ \text{검증·오류 재작업} + \text{도구·라이선스} \\
&+ \text{보안·운영} + \text{위험 여유분}
\end{aligned}
\]

다음 단위로 나누면 견적의 근거를 설명하고 실제 사용량과 비교하기 쉽다.

| 비용 항목 | 수량을 잡는 기준 | 단가 예 | 빠뜨리기 쉬운 부분 |
|---|---|---|---|
| 사람 | 직무별 예상 시간 | 시간당 내부 원가·외주 단가 | 회의, 정의 수정, 검수, 문서화 |
| 데이터 | 획득 건수·기간·갱신 주기 | 구매·API·라벨링 단가 | 사용권한, 정제, 누락 보완 |
| 계산 | CPU·GPU·메모리 사용 시간 | 장비 감가 또는 시간당 서비스 가격 | 대기·실패·재실행·개발 환경 |
| 저장 | 평균 GB × 보관 개월 | GB-월 단가 | 중간 파일, 복제, 백업, 로그 |
| DB·웨어하우스 | 스캔량·쿼리 수·처리 시간 | TB 스캔·요청·시간 단가 | 대시보드 자동 새로고침 |
| API·외부 모델 | 호출 수·입출력량·재시도 | 호출·토큰·이미지당 단가 | 실패 호출, 개발 시험, 환율·한도 |
| 네트워크 | 지역 간·외부 전송 GB | GB당 전송 단가 | 반복 다운로드와 데이터 복제 |
| 검증·재작업 | 검수 건수·오류율·재실행 횟수 | 검수자 시간과 재처리 비용 | 잘못된 지표로 인한 의사결정 비용 |
| 운영·보안 | 월 운영 시간·계정·감사 범위 | 인건비와 서비스 비용 | 권한 회수, 패치, 사고 대응, 복구 시험 |

실제 가격은 장비 세대, 계약, 지역과 서비스에 따라 변한다. 따라서 교재에 적힌 고정 가격을 사용하는 대신 견적 시점의 공식 가격표와 조직 내부 인건비를 넣는다. 비교할 때는 같은 기간과 서비스 수준을 사용한다.

### 일회성 비용과 반복 비용

- **일회성 구축비**: 질문 정의, 데이터 연결, 초기 정제, 코드·대시보드 작성, 보안 검토
- **반복 운영비**: 월별 계산·저장·전송, 데이터 갱신, 품질 감시, 장애 대응, 모델 재평가
- **사용량에 비례하는 비용**: 쿼리 스캔량, API 호출, GPU 시간, 이미지 저장과 전송
- **규모가 커질 때 단계적으로 생기는 비용**: 전담 운영자, 고가용성, 감사·규제 대응, 개발/검증/운영 환경 분리

온프레미스는 일회성 구축비가 크고 반복비가 상대적으로 고정적이며, 클라우드는 구축비가 작고 반복비가 사용량에 따라 움직인다. 같은 표에 두 방식을 나란히 넣어야 비교가 된다.

### 패션 반품 분석의 산정 예

최근 90일 주문으로 카테고리별 반품률을 매주 계산한다고 가정한다. 먼저 금액을 쓰지 않고 수량을 작성한다.

| 항목 | 산정 수량의 예 |
|---|---|
| 분석가 | 질문·지표 정의 12시간 + 분석·검증 28시간 |
| 데이터 엔지니어 | 테이블 연결·권한·배치 구성 16시간 |
| DB | 대표 쿼리 1회 스캔량 × 개발·검증·주간 실행 횟수 |
| 계산 | 노트북 CPU·메모리 사용 시간 + 실패 재실행 예상 시간 |
| 저장 | 결과·중간 파일 GB × 보존 개월 × 원본/백업 사본 수 |
| 운영 | 월별 품질 확인·오류 대응·권한 점검 시간 |
| 보안 | 개인정보 최소화·접근 검토·삭제와 복구 시험 시간 |

그다음 각 수량에 조직의 단가를 곱한다. 작은 표본으로 측정한 실행 시간과 스캔량을 전체 데이터로 확장하되, 데이터가 열 배가 된다고 모든 시간이 정확히 열 배가 된다고 가정하지 않는다. 메모리 한계를 넘거나 동시 사용이 늘면 시스템 구성이 단계적으로 바뀔 수 있다.

## 9. 비용과 분석 가치를 비교한다

분석을 수행할지는 비용이 낮다는 이유만으로 결정하지 않는다. 결과가 바꿀 수 있는 결정의 규모와 실패 비용을 함께 본다.

\[
\text{예상 순가치} = \text{의사결정 개선의 기대효과} - \text{예상 총비용} - \text{위험 비용}
\]

효과를 정확한 금액으로 계산하기 어려우면 범위를 사용한다. 예를 들어 "품절 감소 효과가 월 300만~800만 원이고, 구축비가 2천만 원, 월 운영비가 150만 원"처럼 낙관·기준·비관 시나리오를 나눈다. 작은 파일과 수동 보고서로 먼저 검증한 뒤 반복 가치가 확인되면 DB·배치·대시보드로 확장하는 것도 비용 불확실성을 줄이는 방법이다.

### 알아두면 좋은 경제 원칙: 기회비용과 수확 체감

**기회비용(opportunity cost)**은 지출한 금액만이 아니라, 한 선택 때문에 포기한 대안 중 가장 가치가 큰 것을 뜻한다. 예를 들어 분석가 두 명이 3주 동안 일회성 보고서를 자동화한다면 서버비 외에도 그 기간에 미룬 재고 이상 탐지나 사이즈 안내 개선 실험의 가치가 비용에 포함된다. "예산이 이미 있으니 실행한다"보다 "같은 인력과 시간으로 무엇을 하지 못하게 되는가"를 함께 묻는 이유다.

**수확 체감(diminishing returns)**은 다른 조건이 같을 때 한 자원을 계속 더 투입하면 추가 한 단위가 만드는 개선 폭이 어느 시점부터 작아질 수 있다는 생각이다. GPU를 두 배로 늘렸는데 처리시간이 절반이 되지 않거나, 라벨을 1만 건에서 2만 건으로 늘려도 정확도가 0.2%p만 높아지는 상황을 검토할 때 유용하다. 이는 투자를 멈추라는 법칙이 아니다. 먼저 필요한 품질·보안·완료 시한을 정하고, 그 기준을 충족한 뒤 **추가 비용 대비 추가 개선**을 비교하라는 판단 기준이다.

두 원칙을 함께 쓰면 다음 질문이 생긴다.

- 이 분석에 투입하는 사람·시간·컴퓨팅 자원을 다른 문제에 쓸 때의 가치는 얼마인가?
- 추가 데이터, 더 큰 모델 또는 더 빠른 장비가 만드는 한계 개선은 얼마인가?
- 요구 품질을 충족하는 선택지 가운데 총비용과 위험이 가장 낮은 것은 무엇인가?

- GPU가 지원하는 연산의 비율과 데이터 전송 시간을 확인했는가?

### 환경과 비용

<div class="lesson-section-box lesson-activity-box"><strong>짧은 활동</strong></div>

다음 두 작업의 견적을 만든다.

- 주문 50만 행에서 월별 매출 그래프 작성
- 상품 이미지 100만 장에서 임베딩 생성

각 작업에 대해 데이터의 원시 크기와 예상 메모리, 시작할 CPU/GPU 환경, 로컬·사내 서버·클라우드 가운데 적합한 환경과 이유, 일회성 구축비와 월 반복비를 `사람 시간`, `CPU/GPU 시간`, `GB-월`, `DB 스캔량`, `전송량` 단위로 적는다. 금액은 마지막에 곱한다.

<div class="lesson-section-box lesson-summary-box"><strong>이 장의 핵심</strong></div>

- 견적은 회사 규모가 아니라 데이터량·갱신 속도·동시성·응답 시간·실행 패턴에서 시작한다.
- 5장의 shape×dtype 추정은 최소 크기이며, 실행 중 메모리는 인덱스·문자열·중간 복사본 때문에 더 크다. RAM과 VRAM은 따로 센다.
- CPU는 범용 작업, GPU는 충분한 규모의 지원된 병렬 계산에 맞는다. 선택은 장치 이름이 아니라 표본 측정으로 확인한다.
- Moore의 법칙은 장기 추세일 뿐이므로 견적에는 현재 가격을 쓴다.
- 로컬 장비는 구매·교체, 사내 서버는 큰 초기 구축비와 운영 인력, 클라우드는 월 정액·사용량 과금이라는 서로 다른 비용 성격을 가진다.
- 클라우드 비용은 실행 시간뿐 아니라 저장·스캔·전송·스냅샷과 중지 뒤 남는 자원을 포함한다.
- 총비용은 인건비·데이터·계산·저장·DB·API·전송·검증·운영·보안·위험 여유분의 합이며, 일회성과 반복 비용을 나눈다.
- 도입 여부는 총비용이 아니라 예상 순가치(기대효과 − 총비용 − 위험)로 정하고, 기회비용과 수확 체감을 함께 본다.

## 핵심 용어

- **RAM**: 실행 중인 데이터와 중간 결과를 펼쳐 두는 메모리. 확인: 최대 사용량과 복사본.
- **CPU**: 다양한 명령과 조건을 처리하는 범용 계산 장치. 확인: 코어 수, 실행 시간.
- **GPU**: 같은 형태의 계산을 대량으로 동시에 처리하는 장치. 확인: 지원 코드, VRAM, 전송 시간.
- **VRAM**: GPU 전용 메모리. 확인: 모델과 배치가 들어가는가.
- **가상 머신**: 물리 장비의 자원을 나누어 제공하는 독립 실행 환경. 확인: 크기, 디스크, 시간당 요금.
- **관리형 서비스**: 제공자가 운영 일부를 맡는 DB·노트북·분석 서비스. 확인: 책임 범위, 제한, 사용량 요금.
- **일회성 구축비**: 시작할 때 한 번 드는 비용. 확인: 데이터 연결, 초기 정제, 코드 작성.
- **반복 운영비**: 매달 계속 드는 비용. 확인: 계산·저장·전송, 감시, 장애 대응.
- **총소유비용(TCO)**: 사용 기간 동안 구축·운영·인력·위험을 모두 포함한 비용. 확인: 실행·저장·정제·검증·보안·전환.
- **기회비용**: 한 선택 때문에 포기한 대안 가운데 가장 가치가 큰 것. 확인: 같은 인력·시간으로 못 하게 되는 일.
