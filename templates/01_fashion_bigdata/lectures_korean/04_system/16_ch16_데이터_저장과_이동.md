# Data Storage and Movement

## 학습 목표

패션 데이터 분석가는 서버나 데이터베이스를 직접 구축하지 않더라도 데이터가 놓인 위치와 이동 경로를 알아야 한다. 같은 반품률 분석도 주문 전체를 개인 컴퓨터로 내려받는 방식과 데이터베이스에서 필요한 항목만 집계하는 방식은 속도·비용·보안에서 큰 차이가 난다. 저장과 이동을 이해하는 목적은 시스템 엔지니어가 되는 것이 아니라 **분석에 필요한 시간·비용·인력과 데이터 노출 위험을 판단하는 것**이다.

이 장에서는 데이터베이스 내부 알고리즘, 네트워크 프로토콜이나 서버 설치 명령처럼 패션 데이터 분석가에게 지나치게 기술적인 내용은 다루지 않는다. 대신 데이터가 어디에 있고 왜 이동하는지 설명할 수 있는 수준을 목표로 한다.

이 장을 마치면 다음을 할 수 있다.

- 로컬·클라이언트·서버의 관계를 일상 서비스와 패션 데이터 분석의 예로 설명한다.
- 온프레미스와 클라우드, 플랫폼 서비스의 비용 성격 차이를 설명한다.
- CSV를 내려받을지 데이터베이스에 질의할지, 파일과 DB 중 무엇이 적합한지 판단한다.
- 관계형·컬럼형·문서형·시계열·벡터·Graph·임베디드 DB와 분산 처리 엔진이 각각 어떤 상황에 유리하고 어디서 비용이 생기는지 구분한다.
- 데이터 구조와 파일 형식을 구분하고, YAML이 데이터가 아니라 환경설정에 쓰이는 이유를 설명한다.
- 메모리·캐시·스토리지의 속도·크기·비용·지속성 차이를 설명한다.
- 분석에 필요한 행·컬럼·기간을 데이터가 있는 곳에서 줄여 이동과 사본을 최소화한다.

> **전체 시스템 장을 관통하는 판단 기준**  
> 데이터 분석에는 자원·시간·인력·도구 비용이 발생한다. 분석가는 정확도뿐 아니라 **요구 품질을 충족하는 범위에서 처리시간과 총비용도 함께 관리**해야 한다.

> **시스템 파트의 구성**  
> 이 장은 데이터가 *어디에 있고 어떻게 이동하는지*를, 17장은 시스템을 *도입하기 전에 비용을 어떻게 산정하는지*를, 18장은 도입한 시스템을 *어떻게 운영하고 지키는지*를 다룬다.

> **그림 읽기**
> 내 손에 있는 폰이 **로컬**이고, 그 안에서 요청을 보내는 페이스북 앱이 **클라이언트**다. 요청은 인터넷을 건너 페이스북 **서버**에 도착한다. 서버는 수십억 건의 글 가운데 내가 볼 20개만 골라 작은 응답으로 돌려주고, 앱은 그것을 화면에 그린다. 친구들의 글 전체가 내 폰으로 오는 것이 아니라 **필요한 만큼만 이동**한다.

패션 데이터 분석도 구조가 같다. 분석가의 노트북이 로컬, SQL 도구나 Python 노트북이 클라이언트, 주문 데이터베이스가 서버다. "8월 아우터 순매출"을 조회하면 클라이언트가 SQL을 보내고, 서버가 수천만 건에서 기간·카테고리를 골라 집계한 뒤 상품별 결과 몇백 행만 돌려준다.

여기서 중요한 점은 **화면이 보이는 곳과 계산이 실행되는 곳이 같지 않을 수 있다**는 것이다. 웹브라우저로 코랩 노트북을 보고 있어도 실제 Python 코드는 구글의 서버에서 실행된다. 반대로 DB에서 받은 작은 결과표는 로컬 메모리에서 처리할 수 있다.

### 서버는 누가 소유하는가: 온프레미스와 클라우드

서버라는 컴퓨터는 어딘가에 물리적으로 존재한다. 그것을 누가 사고 관리하느냐에 따라 두 방식으로 나뉜다.

- **온프레미스(on-premises)**: 회사가 서버를 직접 구매해 전산실이나 데이터센터에 두고 운영한다. 장비·네트워크·설치에 드는 **초기 구축 비용이 크고**, 이후에도 전력·냉각·패치·교체 주기와 운영 인력이 필요하다. 사용하지 않는 시간에도 비용이 발생한다.
- **클라우드(cloud)**: AWS, Google Cloud, Azure, 네이버 클라우드 같은 제공자의 서버를 네트워크로 빌린다. 초기 비용은 거의 없고 **월 정액이나 사용량(시간·GB·요청 수)에 따라 요금**을 낸다. 빠르게 시작하고 크기를 바꾸기 쉽지만, 오래 많이 쓰면 총액이 직접 보유보다 커질 수 있고 자원을 끄지 않으면 요금이 계속 나간다.

두 방식의 상세 비교와 비용 산정은 17장에서 다룬다. 이 장에서는 "서버는 어디에나 있을 수 있고, 소유 방식에 따라 비용의 성격이 다르다"는 점만 기억한다.

## 2. 데이터 규모와 기업 규모

### 창업 초기에는 서버를 직접 구성하지 않는다

온라인 패션 브랜드를 시작한다고 해서 서버를 사고 전산실을 꾸밀 필요는 없다. 초기 기업은 트래픽과 데이터가 작고 얼마나 커질지 예측하기 어렵다. 이때 큰 초기 비용은 위험이므로 보통 다음 순서로 시작한다.

1. **플랫폼 서비스**: Shopify, 카페24, 네이버 스마트스토어, 아임웹 같은 서비스는 서버·결제·상품 관리·보안·기본 통계를 월 구독료나 수수료에 포함해 제공한다. 창업자는 서버라는 문제에서 거의 자유로워지고 상품과 고객에 집중한다.
2. **클라우드 위의 자체 서비스**: 플랫폼의 기능 제약이 커지면 클라우드에서 자체 쇼핑몰·앱을 운영한다. 서버는 여전히 빌리지만 구성과 데이터는 직접 통제한다.
3. **자체 데이터 팀과 분석 환경**: 데이터가 쌓이고 분석 요구가 반복되면 데이터 웨어하우스와 분석 파이프라인을 별도로 둔다.

분석가에게 이 순서가 중요한 이유는 **데이터가 있는 곳이 단계마다 다르기 때문**이다. 플랫폼 단계에서는 관리자 화면의 리포트, CSV 내보내기, 앱·API 연동(예: GA4 연결)이 데이터의 출입구다. 클라우드 단계에서는 자체 DB에 직접 질의할 수 있다. 어느 단계든 "우리 데이터는 지금 어디에 있고 어떻게 꺼내는가"를 먼저 답해야 한다.

### 규모는 회사 이름이 아니라 데이터로 잰다

회사 규모가 크다고 모든 분석에 큰 시스템이 필요한 것은 아니다. 작은 브랜드도 고해상도 룩북과 영상을 오래 보관하면 큰 스토리지가 필요하다. 대기업의 한 팀도 익명화된 작은 표본만 분석한다면 노트북으로 충분할 수 있다.

시스템을 정하기 전에 다음을 측정한다.

- 현재 행 수·컬럼 수·파일 크기
- 하루에 새로 생기는 주문·클릭·이미지의 양
- 보관해야 하는 기간과 사본 수
- 동시에 조회하는 사람과 자동 작업의 수
- 결과가 필요한 시점: 몇 초, 몇 분, 다음 날
- 개인정보·출시 전 이미지처럼 민감한 데이터의 포함 여부

| 상황 | 시작하기 좋은 구성 | 추가로 확인할 비용 |
|---|---|---|
| 플랫폼 입점 초기 브랜드 | 플랫폼 리포트 + CSV 내보내기 + 노트북 | 내보내기 한도, 분석가의 정리 시간 |
| 소규모 교육·탐색 데이터 | 로컬 파일 또는 임베디드 DB | 분석가의 정리·백업 시간 |
| 여러 부서의 반복 보고 | 중앙 분석 DB와 예약 작업 | 권한, 쿼리량, 운영 인력 |
| 대량 상품 이미지 | 객체 스토리지와 원격 계산 환경 | 저장량, 전송량, 처리 시간 |
| 서비스와 연결된 실시간 분석 | 운영·분석 환경 분리와 감시 | 응답 시간, 장애 대응, 복구 |

표는 회사를 등급으로 고정하는 기준이 아니다. 작은 표본으로 실행한 뒤 데이터 크기, 읽은 양, 걸린 시간과 동시 사용량을 기록하고 필요한 부분만 확장한다.

## 3. 파일과 데이터베이스의 역할

데이터베이스를 만들고 저장·조회·갱신·권한을 관리하는 소프트웨어를 **DBMS(데이터베이스 관리 시스템)**라고 부르며, 분석가가 SQL을 보내는 대상이 바로 이것이다. 파일과 데이터베이스는 경쟁 관계가 아니다. 하나의 분석에서도 원본은 DB에 있고, 중간 대량 결과는 Parquet으로 저장하며, 최종 검토표는 Excel로 전달할 수 있다.

### 파일이 편리한 상황

- 한 시점의 결과를 고정해 전달할 때
- 비교적 작은 표를 사람이 직접 열어 검토할 때
- 다른 도구로 옮길 수 있는 스냅샷이 필요할 때
- 교육·재현용 표본을 보관할 때

### 데이터베이스가 편리한 상황

- 주문·결제·재고처럼 기록이 계속 추가·변경될 때
- 여러 사용자가 같은 기준의 데이터에 접근할 때
- Key·자료형·중복 방지와 권한을 관리할 때
- 전체가 아닌 필요한 행과 컬럼을 반복 조회할 때

```sql
SELECT product_id, SUM(net_sales) AS sales
FROM order_items
WHERE order_date >= DATE '2026-08-01'
  AND order_date < DATE '2026-09-01'
GROUP BY product_id;
```

이 SQL은 DB가 8월 주문과 필요한 컬럼을 먼저 선택하고 상품별로 집계하게 한다. 전체 주문을 로컬로 내려받아 대부분을 버리는 방식보다 이동량·저장 공간·개인정보 사본을 줄일 수 있다.

## 4. 분석가가 만나는 데이터베이스

DB 종류를 제품 이름으로 외우기보다 **어떤 기록을 어떤 방식으로 넣고 꺼내는가, 그 비용은 어디서 생기는가**로 이해한다. 아래 표는 분석가가 실무에서 이름을 듣게 되는 유형을 상황과 비용 관점에서 정리한 것이다.

| 유형 | 대표 제품 | 유리한 상황 | 비용이 생기는 곳과 주의점 |
|---|---|---|---|
| 관계형(RDB) | PostgreSQL, MySQL | 주문·결제·재고처럼 정확해야 하는 거래 기록, Key로 표를 연결하는 조회 | 서버 1대 또는 관리형 월정액. 무거운 분석 집계를 운영 DB에서 돌리면 주문 처리가 느려진다 |
| 컬럼형·데이터 웨어하우스 | BigQuery, Snowflake, Redshift | 수년치 주문에서 월·채널·카테고리별 집계처럼 많은 행, 적은 컬럼을 읽는 분석 | **스캔한 데이터 양이나 계산 시간에 과금**. 기간·컬럼을 제한하지 않은 쿼리 한 번이 비용이 된다 |
| 문서형 NoSQL | MongoDB, DynamoDB | 상품 옵션·이벤트처럼 구조가 자주 바뀌는 JSON, 대량 쓰기 | 읽기·쓰기 단위 과금 또는 클러스터 비용. 분석 전에 표로 펼치는 정제 작업이 추가된다 |
| Key-Value·캐시 | Redis | 장바구니 상태, 세션, 실시간 카운트처럼 Key로 즉시 찾는 작은 데이터 | 메모리에 두므로 GB당 가장 비싸다. 작고 자주 쓰는 데이터만 올린다 |
| 시계열 DB | InfluxDB, TimescaleDB | 센서·클릭·재고 변동처럼 **초당 수천 건이 시간순으로 들어오는 입력(쓰기)** | 쓰기 처리량과 압축·보존 정책에 최적화. 오래된 데이터는 자동 요약·삭제하므로 원본 보존 기간을 확인한다 |
| 벡터·임베딩 DB | Milvus, Chroma, pgvector | 상품 이미지·설명·리뷰의 임베딩으로 "비슷한 것 찾기"(유사 상품 검색, 추천, RAG) | 벡터 인덱스가 메모리를 많이 쓴다. Chroma는 소규모·프로토타입, Milvus는 수억 벡터의 분산 운영, pgvector는 기존 PostgreSQL에 추가 |
| Graph DB | Neo4j | 고객–상품–브랜드–스타일 태그처럼 여러 단계 관계를 따라가는 탐색 | 관계 탐색에는 편리하지만 단순 매출 합계를 위해 도입할 필요는 없다 |
| 임베디드 분석 DB | DuckDB, SQLite | 서버 없이 노트북의 CSV·Parquet을 SQL로 탐색 | 비용이 거의 0이지만 여러 사람의 동시 접근·중앙 권한 관리가 필요해지면 공용 환경으로 옮긴다 |
| 분산 처리 엔진(DB 아님) | Apache Spark | 수십 GB~TB의 로그·주문을 여러 서버에서 나눠 **변환·집계해 결과를 내보내는 출력(배치)** 작업 | 클러스터를 켠 시간만큼 비용. 데이터가 작으면 노트북의 pandas·DuckDB보다 오히려 느리고 비싸다 |

### 입력에 강한 시스템과 출력에 강한 시스템

같은 "데이터베이스"라도 **들어오는 속도**에 맞춘 시스템과 **꺼내서 계산하는 양**에 맞춘 시스템은 다르다.

- 매장 센서와 앱 클릭이 초당 수천 건 들어온다면 시계열 DB나 문서형 DB처럼 쓰기 처리량에 최적화된 저장소가 먼저 받는다.
- 그 기록을 월 단위로 집계하거나 모델 학습용으로 변환하는 작업은 웨어하우스나 Spark처럼 대량 읽기·계산에 최적화된 도구가 맡는다.
- 계산 결과 가운데 서비스가 즉시 써야 하는 값(추천 목록, 재고 상태)은 Redis 같은 캐시에 올린다.
- 임베딩처럼 "가장 비슷한 것"을 찾는 질문은 벡터 DB가 맡는다.

한 시스템이 모든 역할을 잘하지는 않으므로 실무 환경은 여러 저장소가 이어진 **파이프라인**이 된다. 분석가는 자신이 읽는 표가 이 경로의 어느 지점에서 나온 사본인지 알아야 한다.

### 비용을 읽는 세 가지 축

1. **저장 비용**: 보관하는 GB × 기간. 메모리 기반(Redis, 벡터 인덱스) > SSD 기반 DB > 객체 스토리지 순으로 비싸다.
2. **읽기·계산 비용**: 웨어하우스는 스캔량, Spark는 클러스터 시간, 관리형 NoSQL은 요청 수로 과금한다. 쿼리를 어떻게 쓰느냐가 곧 비용이다.
3. **운영 인력 비용**: 무료 오픈소스도 설치·업데이트·권한·백업·복구를 맡는 사람의 시간이 든다. 관리형 서비스는 그중 일부를 사용료로 대신한다.

시작은 대개 관계형 DB 하나와 파일이면 충분하다. 다른 유형은 "이 질문에 지금 시스템이 느리거나 비싸다"는 측정 결과가 있을 때 추가한다.

## 5. 데이터 파일 형식

6장에서 다룬 것은 데이터의 **구조**(표·문서·그래프)였다. 이 절에서 다루는 것은 그 구조를 파일로 **저장하고 전달하는 형식**이다. 같은 장바구니 문서 구조도 `.json` 파일로 저장할 수도, MongoDB에 넣을 수도, 상품 한 건당 한 행으로 펼쳐 Parquet으로 저장할 수도 있다. 구조는 같아도 형식에 따라 자료형 보존, 읽는 속도, 사람이 검토하기 쉬운 정도, 저장 비용이 다르다.

| 형식 | 잘 맞는 사용 | 주의할 점 |
|---|---|---|
| CSV | 작은 표 전달, 공개 데이터, 플랫폼 내보내기 | 날짜·숫자 자료형을 다시 해석해야 할 수 있음. 압축이 없어 큰 표는 무겁다 |
| Excel | 여러 시트와 서식이 필요한 사람 중심 검토 | 병합 셀·숨김 행·수식이 분석을 혼동시킬 수 있음 |
| Parquet | 큰 분석 표의 저장과 일부 컬럼 읽기 | 사람이 일반 문서처럼 바로 읽기는 어려움. 압축·컬럼 저장으로 CSV보다 저장·스캔 비용이 크게 줄어든다 |
| JSON | 상품 옵션·API 응답·행동 이벤트 같은 계층 데이터 | 분석 전 행과 열로 펼치는 작업이 필요할 수 있음 |
| YAML | 분석 파이프라인·도구의 **환경설정 파일** | 데이터 교환용이 아님. 들여쓰기 오류에 민감하다 |
| DB 테이블 | 지속적으로 갱신되는 공동 데이터 | 쿼리·권한·운영 환경을 이해해야 함 |

### 데이터 형식과 설정 형식은 역할이 다르다

표에서 YAML만 성격이 다르다. 나머지는 주문·상품 같은 **데이터**를 담지만, YAML은 프로그램이 실행될 때 참고하는 **환경설정(configuration)**을 담는다. 환경설정이란 코드 안에 직접 적지 않고 바깥 파일로 빼 둔 실행 조건이다.

```yaml
# 매주 실행하는 반품률 집계 작업의 환경설정 예
source:
  database: fashion_dw          # 어느 DB에서 읽을지
  table: order_items
  lookback_days: 90             # 최근 며칠을 볼지
output:
  path: s3://fashion-analytics/return-rate/   # 결과를 어디에 쓸지
  format: parquet
schedule: "0 6 * * MON"         # 매주 월요일 06:00
```

DB 접속 주소, 읽을 기간, 결과 저장 위치, 실행 주기 같은 값을 여기에 두면 개발 환경과 운영 환경에서 **코드를 바꾸지 않고 설정 파일만 바꿔** 같은 작업을 실행할 수 있다. Docker Compose, GitHub Actions, Kubernetes와 많은 머신러닝 실험 도구가 YAML 설정을 받는다. 비밀번호·API 키는 설정 파일에 적지 않고 환경변수나 비밀 관리 서비스에서 읽는다(18장 참고). 분석가는 YAML 문법을 외우기보다 파이프라인의 설정 파일을 **읽고 기간·경로·임곗값을 바꿀 수 있으면** 충분하다.

형식을 고를 때는 다음을 묻는다.

- 사람이 직접 수정해야 하는가?
- 전체와 일부 컬럼 중 무엇을 자주 읽는가?
- 자료형과 결측값을 유지해야 하는가?
- 파일을 받을 도구가 형식을 지원하는가?
- 접근권한과 보존 기간을 관리할 수 있는가?
- 데이터인가, 실행 조건(설정)인가?

## 6. 메모리·캐시·스토리지: 데이터는 어디에 놓이는가

데이터는 컴퓨터 안팎의 여러 위치에 놓인다. 위치마다 속도, 크기, GB당 비용, 전원을 껐을 때 남는지가 다르다. 분석가가 "지금 이 데이터는 어디에 있는가"를 답할 수 있어야 하는 이유는, 위치가 곧 **속도와 비용과 사본의 위험**을 결정하기 때문이다.

> **그림 읽기**
> 위로 갈수록 빠르고 작고 비싸며 전원이 꺼지면 사라진다. 아래로 갈수록 느리고 크고 GB당 싸며 전원을 꺼도 남는다. 분석 작업은 이 사다리를 **아래에서 위로 데이터를 끌어올려**(스토리지 → 메모리 → CPU) 계산하고, 결과를 **다시 아래로 내려 보관**(메모리 → 파일·DB·객체 스토리지)하는 과정이다.

### 메모리: 계산이 일어나는 곳

Python에서 `pd.read_csv()`를 실행하면 파일이 스토리지에서 메모리로 올라온다. 계산은 메모리 위의 데이터로 이루어진다. 4GB CSV를 읽으면 메모리에서는 자료형과 인덱스 때문에 그보다 커질 수 있고, 두 표를 합치는 동안에는 원본과 결과가 함께 존재한다. 메모리보다 큰 데이터를 올리려 하면 오류가 나거나 극도로 느려진다. 노트북 런타임이 꺼지면 메모리의 변수는 사라지므로 결과는 파일이나 DB로 내려 보관한다.

### 캐시: 같은 개념이 여러 층에 나타난다

캐시는 특정 장치의 이름이 아니라 **자주 쓰는 데이터의 사본을 더 가까운 곳에 두는 방법**이다. CPU 캐시는 메모리에서 방금 읽은 값을 프로세서 안에 두고, 브라우저 캐시는 한 번 받은 상품 이미지를 로컬 디스크에 두어 다시 내려받지 않게 하며, Redis 같은 캐시 서버는 DB에서 계산한 추천 목록을 메모리에 두어 매 요청마다 DB를 다시 읽지 않게 한다. 노트북에서 큰 집계 결과를 변수나 Parquet으로 저장해 두고 재사용하는 것도 같은 원리다.

캐시의 대가는 **오래된 사본**이다. 원본이 바뀌었는데 캐시가 갱신되지 않으면 어제 가격이 보이거나 품절 상품이 추천된다. 캐시를 쓸 때는 얼마나 오래 유지할지(TTL)와 언제 지울지를 정한다.

### 스토리지: 전원을 꺼도 남는 곳

분석가가 자주 만나는 스토리지 위치는 세 곳이다.

- **로컬 SSD**: 작은 표본을 빠르게 읽고 쓰기 좋다. 그러나 고장·분실·개인 동기화와 승인되지 않은 사본 위험을 사용자가 직접 관리해야 한다.
- **공용 파일 저장소·DB**: 팀이 정한 폴더 구조와 권한으로 결과를 공유한다. 복사본이 여러 폴더에 흩어지지 않도록 원본·중간·최종 상태와 담당자를 정한다.
- **객체 스토리지**: 이미지·영상·Parquet·모델 파일처럼 큰 객체를 Key와 경로로 보관한다. GB당 가장 싸지만 저장 단가뿐 아니라 읽기 요청, 버전, 백업, 다른 지역이나 외부로 내보내는 전송비가 생긴다.

저장 비용은 단순히 `현재 파일 GB × 단가`가 아니다.

\[
\text{저장 관련 비용} = \text{평균 저장량} \times \text{보관 기간} \times \text{사본 수} + \text{요청·전송·관리 비용}
\]

중간 결과, 자동 백업, 로그와 이전 버전도 사본 수에 포함한다. 이 데이터가 메모리에 얼마나 필요한지 추정하고 CPU·GPU를 고르는 일은 17장에서, 병목을 찾고 운영하는 일은 18장에서 다룬다.

## 7. 데이터 이동과 네트워크

분석 시간에는 계산뿐 아니라 DB에서 서버로, 스토리지에서 메모리로, 서버에서 로컬로 데이터를 옮기는 시간이 포함된다.

원격 DB의 주문 5천만 건을 모두 내려받으면 다음 비용이 생긴다.

- DB가 데이터를 읽고 결과를 만드는 시간
- 네트워크 대기와 전송량
- 로컬 저장과 다시 읽는 시간
- 개인정보 사본의 접근·보관·삭제 책임
- 원본이 갱신됐을 때 다시 내려받는 재작업

상품별 월간 주문 수만 필요하다면 데이터가 있는 DB에서 먼저 집계해 몇백 행만 받는 편이 적절하다. 이미지 분석도 원본 이미지 가까이에서 임베딩을 계산하고 필요한 벡터와 요약만 이동하는 방식을 검토할 수 있다.

> **데이터 이동 최소화의 원칙**  
> 질문에 필요한 행·컬럼·기간과 집계 수준을 먼저 정하고, 가능한 경우 데이터가 저장된 곳에서 줄인 뒤 이동한다. 페이스북이 친구들의 글 전체가 아니라 내가 볼 20개만 보내는 것과 같은 원리다.

## 8. 운영 데이터와 분석 환경

운영 DB의 우선 목적은 주문·결제·재고 같은 일상 업무를 안정적으로 처리하는 것이다. 분석가의 큰 JOIN이나 수년치 집계가 운영 업무와 같은 자원을 경쟁하면 고객 서비스가 느려질 수 있다.

조직은 필요에 따라 다음 환경을 사용한다.

- **읽기 복제본**: 운영 DB의 데이터를 복제해 조회 부하를 분리한다.
- **데이터 웨어하우스**: 여러 운영 시스템의 이력을 분석하기 좋은 형태로 모은다.
- **데이터 마트**: 상품기획·마케팅·재고 등 특정 업무의 공통 지표를 제공한다.
- **승인된 파일 영역**: 일회성 분석의 표본과 결과를 통제된 공간에서 관리한다.

분석만을 위한 데이터 수집 시스템을 별도로 구축하는 경우도 있다. 그러나 기대되는 분석 이익보다 구축·운영비가 크면 지속하기 어렵다. 특히 초기에는 필요한 데이터량, 정제 난이도, 반복 횟수와 사람 시간을 정확히 예측하기 어렵다. 작은 범위로 가치와 비용을 측정한 뒤 확장하는 이유다.

## 9. 분석 과정에서 생기는 사본

원본 이외에도 다음 데이터가 생긴다.

- 내려받은 CSV·Excel
- 전처리한 중간 표와 임시 파일
- 노트북 출력과 캐시
- 그래프·대시보드용 집계표
- 스토리지 버전, 스냅샷, 백업과 로그

각 사본에는 최소한 다음 정보를 연결한다.

- 누가 만들고 관리하는가?
- 원본과 생성 기준은 무엇인가?
- 누가 읽을 수 있는가?
- 언제 갱신되고 언제 삭제되는가?
- 다시 만들 수 있는가, 반드시 백업해야 하는가?

사본을 줄이면 저장비뿐 아니라 잘못된 버전을 사용할 가능성과 개인정보 노출 범위도 줄어든다.

## 10. 패션 반품 분석의 데이터 경로

최근 90일 카테고리별 반품률을 매주 계산한다고 가정한다.

1. 주문·상품·반품 원본은 각 운영 시스템에 기록된다.
2. 승인된 분석 DB나 웨어하우스에 필요한 이력이 준비된다.
3. SQL에서 기간·완료 주문·반품 상태와 필요한 컬럼을 선택한다.
4. 카테고리별 집계 결과와 품질 확인용 표본만 분석 환경으로 가져온다.
5. Python에서 그래프와 예외 항목을 확인한다.
6. 최종 결과는 권한이 통제된 프로젝트 저장소에 버전과 함께 보관한다.
7. 중간 파일은 정한 기간 뒤 삭제하고 매주 실행한 기록을 남긴다.

이 경로에서 분석가는 "원본은 어디 있는가, 어느 단계에서 행 수가 줄어드는가, 어떤 사본이 남는가"를 설명할 수 있어야 한다.

<div class="lesson-section-box lesson-summary-box"><strong>이 장의 핵심</strong></div>

- 로컬은 내 기기, 클라이언트는 요청을 보내는 프로그램, 서버는 네트워크 너머에서 응답하는 컴퓨터다. 화면이 보이는 곳과 계산되는 곳은 다를 수 있다.
- 서버는 직접 사서 운영하는 온프레미스(초기 구축비 큼)와 빌려 쓰는 클라우드(월 정액·사용량 과금)로 나뉜다.
- 창업 초기에는 서버를 직접 구성하지 않고 Shopify·카페24 같은 플랫폼이나 클라우드에서 시작하며, 데이터의 출입구는 단계마다 다르다.
- 시스템 규모는 회사 이름보다 데이터량·동시성·응답 시간·민감도로 판단한다.
- 파일은 전달과 스냅샷에, DB는 지속적 갱신·조회·권한 관리에 적합하다.
- DB 유형은 입력 속도(시계열·문서형), 대량 출력·계산(웨어하우스·Spark), 즉시 조회(캐시), 유사도 검색(벡터 DB)처럼 맡는 역할이 다르고 비용이 생기는 곳도 다르다.
- 6장의 구조와 달리 파일 형식은 저장·전달 방식이며, YAML은 데이터가 아니라 환경설정에 쓴다.
- 데이터 위치는 CPU 캐시 → 메모리 → 캐시 서버 → 로컬 스토리지 → DB·공유 저장소 → 객체 스토리지로 내려갈수록 느리고 크고 싸며 오래 남는다.
- 필요한 행·컬럼·기간을 데이터가 있는 곳에서 줄이면 이동 시간·전송비·사본을 줄일 수 있다.
- 운영 데이터와 분석 환경을 분리하는 이유는 안정성·성능·권한 관리에 있다.

## 핵심 용어

- **로컬**: 내가 직접 손에 쥐고 있는 기기와 그 안의 저장 공간. 예: 내 노트북, 내 스마트폰.
- **클라이언트**: 서버에 요청을 보내고 결과를 받는 프로그램. 예: 페이스북 앱, 웹브라우저, SQL 도구, Python 노트북.
- **서버**: 네트워크 너머에서 요청을 받아 데이터나 계산을 돌려주는 컴퓨터·프로그램. 예: 페이스북 데이터센터, 사내 DB 서버.
- **온프레미스**: 회사가 서버를 직접 사서 자기 공간에 두고 운영하는 방식. 예: 본사 전산실의 주문 DB 서버.
- **클라우드**: 다른 회사의 서버를 네트워크로 빌려 쓰고 사용량·기간에 따라 요금을 내는 방식. 예: AWS, Google Cloud, Azure, 네이버 클라우드.
- **DBMS**: 데이터의 저장·조회·갱신·권한을 관리하는 시스템. 예: 주문·상품·재고 데이터베이스.
- **메모리(RAM)**: 실행 중인 프로그램과 데이터를 펼쳐 두는 공간. 전원이 꺼지면 사라진다. 예: 노트북에 올린 DataFrame.
- **캐시**: 자주 쓰는 데이터의 사본을 더 가까운 곳에 두어 다시 가져오는 시간을 줄이는 장치. 예: CPU 캐시, 브라우저 캐시, Redis.
- **스토리지**: 전원을 꺼도 데이터가 남는 보관 공간. 예: SSD, 공유 드라이브, 객체 스토리지.
- **사본**: 원본을 복제해 만든 별도 데이터. 예: 분석용 테이블, 내려받은 CSV, 백업.
