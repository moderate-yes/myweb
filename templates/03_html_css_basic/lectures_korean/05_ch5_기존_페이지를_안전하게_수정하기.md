# Safely Modifying and Verifying an Existing Page

## 학습 목표

한 곳을 고쳤더니 다른 강의 화면이나 모바일 레이아웃이 깨지는 일은 흔하다. 이 장은 기존 페이지를 수정할 때 요청을 분류하고, 영향 범위를 확인하며, 되돌릴 수 있게 작업하는 절차를 다룬다.

이 장을 마치면 다음을 할 수 있다.

- 수정 요청을 내용·구조·스타일로 분리한다.
- 기존 class와 원본 파일을 찾아 최소 범위로 수정한다.
- 접근성·좁은 화면·다른 문서에 미치는 영향을 점검한다.
- 생성형 AI가 제안한 HTML·CSS를 검토하고 되돌릴 수 있게 기록한다.

## 1. 요청을 세 종류로 나눈다

“그래프 아래에 출처를 넣고 표를 회색으로 정리해 줘”라는 요청에는 서로 다른 작업이 섞여 있다.

- **내용**: 어떤 출처 문구와 링크를 넣을지 결정한다.
- **HTML 구조**: 그래프를 `figure`로 묶고 `figcaption`을 추가한다.
- **CSS 표현**: 해당 표 class의 배경·테두리·간격을 조정한다.

이 구분 없이 HTML과 CSS를 한꺼번에 크게 바꾸면 문제 원인을 찾기 어렵다. 먼저 내용의 정확성을 확정하고 구조를 고친 뒤 표현을 조정한다.

## 2. 안전한 수정의 기본 순서

1. **재현**: 문제가 보이는 주소, 화면 크기와 문서를 기록한다.
2. **대상 찾기**: 검사 도구에서 태그·class·적용 CSS 파일을 확인한다.
3. **원본 확인**: 생성 결과가 아니라 실제 원본 파일을 찾는다.
4. **영향 범위 검색**: 바꾸려는 class가 다른 문서에서도 쓰이는지 검색한다.
5. **최소 수정**: 새 구조와 스타일을 가능한 작은 범위에 적용한다.
6. **비교 검증**: 수정한 문서, 다른 문서와 좁은 화면을 확인한다.
7. **기록**: 무엇을 왜 바꿨고 어떻게 확인했는지 남긴다.

## 3. 실전 예: 그래프에 출처를 추가하고 카드만 수정하기

수정 전에는 이미지와 출처가 서로 분리되어 있다.

```html
<img src="images/return_rate.png" alt="반품률 그래프">
<p>출처: 주문 데이터</p>
```

수정 뒤에는 의미 단위로 묶고, 역할 class를 붙인다.

```html
<figure class="analysis-figure">
  <img
    src="images/return_rate.png"
    alt="사이즈별 반품률은 S 6.1%, M 8.4%, L 12.7%로 L이 가장 높다"
  >
  <figcaption>
    그림 1. 사이즈별 반품률. 2026년 8월 배송 완료 주문 기준이며 교환은 제외했다.
    <a href="metric-definition.html">반품률 정의</a>
  </figcaption>
</figure>
```

```css
.analysis-figure {
  margin: 24px 0;
}

.analysis-figure figcaption {
  margin-top: 8px;
  color: #555;
  font-size: 0.875rem;
}
```

`figure` 전체나 모든 `figcaption`을 바꾸지 않고 프로젝트에서 합의한 `.analysis-figure` 범위로 제한한다. 단, 이미 같은 class가 있다면 새 규칙을 추가하기 전에 기존 의미와 사용 위치를 확인한다.

## 4. 검증표: 보이는 것과 의미를 함께 확인한다

### 콘텐츠

- 숫자·기간·분모·단위와 제외 규칙이 원자료와 같은가?
- 링크 문구가 목적지를 설명하고 실제 주소가 열리는가?
- 표와 그래프가 같은 지표 정의와 갱신 시점을 사용하는가?

### HTML 구조와 접근성

- 제목 단계가 `h1` → `h2` → `h3` 순으로 자연스러운가?
- 표에 caption과 열 머리글이 있는가?
- 정보 이미지에 의미 있는 alt가 있는가?
- 키보드만으로 링크와 펼침 영역을 사용할 수 있는가?

### CSS와 화면

- 수정한 선택자가 다른 페이지까지 바꾸지 않는가?
- 320~400px 정도의 좁은 화면에서 글자·표·이미지가 잘리지 않는가?
- 확대했을 때 글자와 버튼이 겹치지 않는가?
- 색만으로 정상·경고를 구분하지 않는가?

## 5. 생성형 AI에 요청할 때 필요한 맥락

나쁜 요청은 “표 예쁘게 해 줘”처럼 대상과 제약이 없다. 다음 정보를 함께 주면 불필요한 전체 재작성을 줄일 수 있다.

```text
목표: 이 분석 표 하나의 가독성 개선
수정 가능: result-table class의 CSS와 표를 감싸는 div
유지할 것: 표 데이터, 열 순서, 기존 색상 체계
필수 검증: 360px 화면에서 모든 열 확인 가능, 다른 table에는 영향 없음
금지: JavaScript 추가, 인라인 style, !important
```

AI가 제안한 코드는 바로 전체 파일에 붙이지 않는다. 선택자가 존재하는지, 닫는 태그가 맞는지, 속성 이름과 단위가 유효한지 확인하고 작은 범위에서 시험한다. 실제 고객 데이터나 비공개 내부 주소는 프롬프트에 넣지 않는다.

## 6. 문제 발생: 수정한 페이지는 맞지만 다른 페이지가 깨진다

`table`, `img`, `h2` 같은 전역 선택자를 바꾸면 같은 스타일 파일을 쓰는 모든 문서가 영향을 받을 수 있다. 원래 규칙을 무작정 덮어쓰지 말고 다음을 확인한다.

- 변경한 선택자가 몇 곳에서 사용되는가?
- 기존 class를 더 구체적인 영역 안에서 재사용할 수 있는가?
- 새 class가 필요하다면 콘텐츠 역할을 정확히 표현하는가?
- 공통 스타일을 수정해야 한다면 대표 문서들을 함께 확인했는가?

버전 관리가 있다면 수정 전 상태를 보존하고 변경 차이를 읽는다. 한 번에 구조·색·간격·문구를 모두 바꾸기보다 의미 있는 작은 단위로 나누면 원인을 찾고 되돌리기 쉽다.

## 최종 실습

분석 결과 조각 하나를 골라 다음 산출물을 만든다.

1. `section` 또는 `article` 안에 제목·해석·주의점을 구조화한다.
2. 표 하나에 caption, thead, tbody와 적절한 th를 적용한다.
3. 그래프 하나에 구체적인 alt와 figcaption을 추가한다.
4. 역할을 나타내는 class 두 개 이하로 필요한 범위만 스타일링한다.
5. 일반 화면과 360px 좁은 화면을 비교한다.
6. 변경 이유와 확인 결과를 세 문장으로 기록한다.

## 이 장의 핵심

- 수정 요청을 내용, HTML 구조와 CSS 표현으로 나누면 오류를 찾기 쉽다.
- 검사 도구에서 대상을 찾고 원본과 사용 범위를 확인한 뒤 최소 수정한다.
- 화면이 예뻐진 것만으로 완료가 아니며 숫자·의미·접근성·좁은 화면을 함께 검증한다.
- 생성형 AI의 코드도 선택자, 영향 범위와 실제 화면을 사람이 확인해야 한다.
- 변경 전후를 비교하고 되돌릴 수 있어야 안전한 편집이다.

1. 생성된 HTML 파일보다 원본 템플릿이나 Markdown을 찾아야 하는 이유는 무엇인가?

3. 분석 그래프를 수정한 뒤 시각적 확인 외에 검증할 항목 세 가지를 쓰시오.
