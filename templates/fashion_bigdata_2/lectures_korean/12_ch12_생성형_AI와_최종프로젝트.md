# 생성형 AI와 검증 가능한 패션 데이터 프로젝트

생성형 AI 시대의 핵심 역량은 특별한 주문 문구를 외우는 것이 아니다. **업무를 명확히 정의하고, 필요한 근거를 연결하며, 결과를 검사하고, 자동화가 멈춰야 할 지점을 정하는 능력**이다.

이 장에서는 생성형 AI를 한 번에 정답을 내는 기계가 아니라 `질문 → 근거 → 생성 → 구조 검사 → 사실 검증 → 사람 승인 → 결과 관찰`의 업무 시스템으로 다룬다.

## 학습 목표

- 프롬프트를 마법 문구가 아니라 작업 계약으로 작성한다.
- 모델의 내부 기억과 제공된 근거를 구분한다.
- RAG의 검색 단계와 생성 단계를 분리해 설명한다.
- 표·JSON 같은 구조화 출력의 형식과 내용 정확성을 따로 검사한다.
- AI 에이전트의 읽기·쓰기·외부 전송 권한과 사람 승인 지점을 설계한다.
- 작은 평가셋으로 품질·비용·속도·위험을 비교한다.
- AI가 만든 SQL·Python·보고서의 결과를 원자료와 반례로 검증한다.

## 핵심 용어

- **작업 계약(task contract)**: 목표, 입력, 근거, 제약, 출력 형식과 평가 기준을 명시한 업무 정의.
- **Grounding**: 모델의 답을 확인 가능한 문서·데이터·도구 결과에 연결하는 것.
- **RAG(Retrieval-Augmented Generation)**: 질문과 관련된 자료를 먼저 검색한 뒤 그 자료를 문맥으로 제공해 답을 생성하는 구조.
- **구조화 출력(structured output)**: 표나 JSON처럼 필드와 자료형이 정해진 결과.
- **에이전트(agent)**: 모델이 파일·검색·데이터베이스·업무 도구를 사용해 여러 단계를 수행하는 시스템.
- **평가셋(evaluation set)**: 실제 업무를 대표하는 입력과 기대 조건을 모아 반복적으로 품질을 확인하는 사례 묶음.
- **사람 승인(human approval)**: 외부 공개·고객 접촉·결제·삭제처럼 영향이 큰 행동 전에 책임자가 결과와 근거를 확인하는 절차.

## 1. 프롬프트보다 먼저 업무를 정의한다

“이번 시즌 트렌드를 분석해 줘”는 작업 범위도 성공 기준도 불명확하다. 결과가 그럴듯해도 무엇을 근거로 판단했는지 검사하기 어렵다.

| 작업 계약 요소 | 확인 질문 | 패션 상품기획 예시 |
|---|---|---|
| 결정 | 결과로 무엇을 결정할 것인가? | 다음 달 테스트할 아우터 소재 후보 3개 |
| 대상·기간 | 누구와 언제의 자료인가? | 국내 여성 고객, 최근 8주 |
| 입력 | 어떤 원자료를 사용할 것인가? | 검색어·판매·반품·리뷰 |
| 근거 범위 | 어떤 자료 밖의 사실을 만들면 안 되는가? | 제공한 내부 자료와 공식 시장 보고서만 사용 |
| 제약 | 하지 말아야 할 것은 무엇인가? | 개인 식별정보 출력 금지, 인과관계 단정 금지 |
| 출력 | 어떤 스키마로 반환할 것인가? | 후보·근거·반대 근거·확인 필요 항목 표 |
| 평가 | 성공과 실패를 어떻게 판정하는가? | 인용 일치, 계산 재현, 누락·추측 표시 |
| 승인 | 누가 다음 행동을 결정하는가? | MD가 원자료를 확인한 뒤 샘플 제작 승인 |

> **중심 원칙**
> 좋은 프롬프트는 문장이 길어서 좋은 것이 아니다. 실제 결정과 근거, 금지 조건, 출력 형식과 평가 기준이 연결되어야 한다.

Zero-shot·few-shot 같은 용어는 참고 개념이다. 예시는 원하는 형식을 보여주는 데 도움이 되지만 사실 정확성을 보장하지 않는다. 특정 문구나 “단계별로 생각해”라는 요청도 검증을 대신하지 않는다.

## 2. 모델의 기억과 확인 가능한 근거를 분리한다

언어모델은 학습한 패턴을 바탕으로 다음 표현을 생성한다. 따라서 유창한 설명과 확인된 사실은 다르다. 날짜·가격·법·제품 사양·논문 결과처럼 바뀌거나 정확성이 중요한 정보는 원문을 찾아야 한다.

| 답의 근거 | 사용할 수 있는 상황 | 반드시 표시할 한계 |
|---|---|---|
| 모델의 일반 지식 | 아이디어 초안, 질문 목록, 문장 구조 | 최신성·정확성·출처가 보장되지 않음 |
| 사용자가 제공한 문서 | 문서 요약·비교·필드 추출 | 문서 자체의 오류와 누락은 남음 |
| 검색으로 찾은 자료 | 최신 사실·정책·논문 확인 | 검색 누락, 출처 품질, 인용 불일치 점검 필요 |
| 데이터베이스·분석 도구 | 주문·재고·행동 지표 계산 | 쿼리·조인·필터·분모가 틀릴 수 있음 |
| 사람의 현장 판단 | 제작 가능성·브랜드·고객 맥락 | 경험의 편향과 설명 책임이 남음 |

RAG는 모델을 자동으로 진실하게 만들지 않는다. 검색이 잘못된 문서를 가져오거나, 중요한 표의 일부를 놓치거나, 생성 단계가 근거보다 강한 주장을 만들 수 있다. 다음을 따로 평가한다.

1. 필요한 자료가 검색 후보에 들어왔는가?
2. 선택한 구간이 질문에 실제로 관련 있는가?
3. 답의 각 주장이 해당 근거에서 확인되는가?
4. 근거가 없을 때 “확인할 수 없음”이라고 말하는가?

## 3. 구조가 맞는 것과 내용이 맞는 것은 다르다

AI가 다음 JSON을 반환했다고 하자.

```json
{
  "product_id": "P501",
  "recommended_action": "restock",
  "evidence": ["최근 7일 판매 증가"],
  "confidence": 0.92
}
```

필드와 따옴표가 올바르다고 재입고 판단까지 올바른 것은 아니다.

| 검사 층 | 확인 내용 | 실패 예 |
|---|---|---|
| 형식 | 필수 필드, 자료형, 허용값 | `confidence`가 문자열, 상품 ID 누락 |
| 데이터 | 실제 존재하는 ID와 기간인가? | 없는 상품 ID, 미래 날짜 사용 |
| 계산 | 판매 증가율과 분모가 재현되는가? | 취소 주문 포함, 0으로 나눔 |
| 의미 | 근거가 행동을 지지하는가? | 판매 증가만으로 수익성·지속 수요 단정 |
| 정책 | 자동 실행이 허용되는가? | 승인 없이 발주·가격 변경 |

구조화 출력은 시스템 연결에 유용하다. 그러나 스키마 검사는 문법적 안전장치이고, 사실·업무 타당성 검사는 별도 단계다.

## 4. AI가 만든 SQL과 Python은 작은 반례로 시험한다

코드가 실행되었다는 것은 문법 오류가 없다는 뜻이지 분석 질문에 맞았다는 뜻이 아니다. 다음 검증표를 공통으로 사용한다.

| 검사 | 질문 | 간단한 시험 |
|---|---|---|
| 입력 | 어떤 파일·테이블·컬럼을 사용했는가? | 스키마와 dtype 출력 |
| 행 보존 | JOIN 전후 행 수가 예상과 같은가? | 키 중복·미매칭 수 확인 |
| 필터 | 취소·반품·기간을 정확히 제외했는가? | 포함/제외 예시 행 5개 대조 |
| 결측 | 결측을 0과 혼동하지 않았는가? | 결측·0·빈 문자열 각각 시험 |
| 경계값 | 데이터가 0건·1건일 때 동작하는가? | 빈 표와 단일 행 입력 |
| 계산 | 손으로 확인 가능한 작은 표와 일치하는가? | 3~5행 기대값 작성 |
| 재현 | 같은 입력과 버전에서 다시 만들 수 있는가? | 입력·코드·환경·실행일 기록 |

AI에게 코드를 설명하게 하는 것만으로 검증을 끝내지 않는다. 설명도 코드와 같은 모델이 만든 출력일 수 있으므로 실제 작은 데이터와 기대 결과를 비교한다.

## 5. 에이전트는 답이 아니라 행동 권한을 가진다

AI가 파일을 읽거나 검색만 할 때와 고객에게 메시지를 보내거나 가격을 바꿀 때의 위험은 다르다.

| 권한 단계 | 예 | 기본 통제 |
|---|---|---|
| 읽기 | 문서·재고·주문 조회 | 최소 범위, 개인정보 마스킹, 접근 로그 |
| 초안 | 보고서·메일·상품 설명 작성 | 외부 전송 금지, 출처와 변경점 표시 |
| 제한된 쓰기 | 승인된 필드에 태그 추가 | 허용값·건수 제한, 되돌리기, 샘플 검토 |
| 외부 행동 | 고객 메시지, 가격·재고·광고 변경 | 실행 직전 사람 승인, 금액·대상 제한 |
| 고위험 행동 | 결제·계약·대량 삭제 | 자동 실행 금지 또는 이중 승인 |

### 에이전트 실행 계약

- 사용할 수 있는 데이터와 도구의 최소 범위
- 한 번에 처리할 수 있는 고객·상품·금액의 상한
- 확인되지 않은 입력이나 도구 오류가 있을 때 중단하는 조건
- 외부 전송·삭제·가격 변경 전 승인자
- 모든 입력, 도구 호출, 결과와 승인 기록
- 실패 시 되돌리는 방법과 책임자

> **즉시 해석**
> 자동화 수준이 높아질수록 사람은 모든 중간 문장을 읽는 대신 권한, 평가셋, 예외, 승인과 사후 모니터링을 더 정확히 설계해야 한다.

## 6. 느낌이 아니라 작은 평가셋으로 비교한다

모델이나 프롬프트 후보를 한두 개의 보기 좋은 결과로 선택하지 않는다. 실제 업무의 정상 사례, 어려운 사례와 실패하면 위험한 사례를 모은다.

| 평가 사례 | 입력 | 기대 조건 | 실패 비용 |
|---|---|---|---|
| 일반 상품 설명 | 승인된 소재·치수표 | 사실과 금지 표현 준수 | 낮음 |
| 옵션이 복잡한 상품 | 색·사이즈별 상이한 재고 | 옵션 혼합 금지 | 중간 |
| 반품 관련 답변 | 정책 버전과 주문 상태 | 정책 인용·예외 시 사람 연결 | 높음 |
| 가격 제안 | 원가·재고·할인 규칙 | 하한 준수·자동 변경 금지 | 높음 |
| 개인정보 포함 문의 | 고객 메시지 | 불필요한 개인정보 재출력 금지 | 매우 높음 |

평가 결과에는 정확도 하나만 쓰지 않는다.

- **품질**: 사실 일치, 누락, 근거 인용, 형식 통과율
- **안전**: 개인정보, 차별, 금지 주장, 권한 초과
- **업무 성과**: 검토 시간, 수정률, 고객 해결률, 반품·문의
- **운영성**: 응답 시간, 실패율, 재현성, 변경 감지
- **비용**: 모델 사용료뿐 아니라 데이터 준비·검수·재작업 비용

정확도가 조금 높아도 비용과 지연이 지나치거나 중요한 실패를 숨긴다면 더 좋은 선택이 아닐 수 있다.

## 7. 사람은 어디에서 최종 책임을 져야 하는가

| 업무 | AI가 도울 수 있는 부분 | 사람이 승인할 부분 |
|---|---|---|
| 트렌드 탐색 | 대량 문서 요약·후보 묶기 | 출처 품질, 신규성, 브랜드 적합성 |
| 상품 카피 | 형식에 맞는 초안 생성 | 실제 소재·기능·광고 주장 |
| 이미지 시안 | 배경·구도 후보 생성 | 제품 충실도, 인물·저작권, 소비자 오인 |
| 고객 응대 | 정책 검색·답변 초안 | 예외 처리, 보상·분쟁, 개인정보 |
| 재고 판단 | 이상 신호와 시나리오 제시 | 발주 비용, 현장 제약, 중단 조건 |

사람 검토는 형식적인 마지막 클릭이 아니다. 승인자가 볼 근거와 실패 사례가 함께 제공되어야 하며, 충분히 검토할 시간과 거절 권한이 있어야 한다.

## 최종 프로젝트: 검증 가능한 패션 데이터·AI 업무 카드

앞 장에서 수행한 분석 하나와 연결되는 패션 업무를 고른다. 예를 들어 상품 텍스트 분석→검색 설명 개선, 이상치 탐지→재입고 후보 검토, 이미지 유사도→대체 상품 추천, 퍼널 분석→사이즈 안내 실험으로 이어갈 수 있다.

먼저 비즈니스 질문, 분석 단위, 입력 기간, 제외 규칙, 기준선과 결과가 말하지 못하는 것을 기록한다. 그다음 생성형 AI가 맡을 작업과 사람이 최종 판단할 범위를 정한다.

| 항목 | 작성 |
|---|---|

마지막으로 다음 문장을 완성한다.

> “AI는 ___까지 수행한다. 결과는 ___ 근거와 ___ 평가셋으로 검사하며, ___ 행동 전에는 ___이 승인한다. ___이 발생하면 자동화를 중단하고 ___로 되돌린다.”

## 이 장의 핵심

- 생성형 AI 시대의 핵심 역량은 프롬프트 문구 암기가 아니라 검증 가능한 업무 설계다.
- 모델의 일반 지식, 제공 문서, 검색 결과, 데이터 계산과 사람 판단은 서로 다른 근거다.
- RAG는 검색과 생성을 연결하지만 검색 누락·근거 선택·인용 불일치를 각각 평가해야 한다.
- 구조화 출력이 스키마를 통과해도 사실과 업무 판단은 틀릴 수 있다.
- AI가 만든 SQL·Python은 작은 기대값, 행 수, 결측, 경계값과 반례로 시험한다.
- 에이전트는 최소 권한, 한도, 승인, 중단, 기록과 되돌리기가 필요하다.
- 모델 선택보다 먼저 실제 업무를 대표하는 평가셋과 실패 비용을 정의한다.
- 품질·속도·비용·프라이버시·책임의 trade-off를 사람이 결정한다.

## 학습 점검

1. 긴 프롬프트와 좋은 작업 계약은 어떻게 다른가?
2. RAG에서도 사실 오류가 발생할 수 있는 세 단계를 쓰시오.
3. JSON 형식이 유효해도 추천 행동이 틀릴 수 있는 이유는 무엇인가?
4. AI가 작성한 집계 코드에 사용할 작은 반례 두 가지를 쓰시오.
5. 에이전트가 고객 메시지를 보내기 전에 필요한 통제를 세 가지 쓰시오.
6. 모델 평가에서 정확도와 함께 비용·안전 지표를 봐야 하는 이유는 무엇인가?

<details>
<summary>정답과 해설 보기</summary>

1. 긴 프롬프트는 단지 문장이 많을 수 있지만 작업 계약은 실제 결정, 입력·근거, 금지 조건, 출력 형식, 평가와 승인자를 연결한다.
2. 필요한 문서를 검색하지 못함, 관련 없는 구간을 선택함, 생성한 주장이 선택한 근거와 일치하지 않음 등이 있다.
3. 스키마는 필드와 자료형만 검사하며 데이터의 최신성, 계산, 인과 해석과 업무 정책까지 보장하지 않기 때문이다.
4. 빈 표, 한 행, 결측과 0이 함께 있는 표, 중복 키가 있는 JOIN, 취소 주문이 포함된 표 등이 있다.
5. 대상·건수 제한, 개인정보 점검, 답변 근거, 사람 승인, 전송 로그, 중단·되돌리기 등이 있다.
6. 작은 품질 향상이 큰 비용·지연·개인정보 위험이나 치명적 실패를 정당화하지 못할 수 있기 때문이다.
