# 데이터를 묶고 연결하는 법: Table·JSON·Network

값의 의미와 타입을 이해했다면 다음 질문은 **여러 값을 어떤 구조로 묶을 것인가**이다. 고객·상품·주문·재고처럼 행과 열이 뚜렷한 데이터도 있지만, 한 장바구니 안의 여러 상품 옵션이나 고객–상품–브랜드 사이의 연결은 다른 구조가 더 자연스러울 수 있다.

Excel처럼 보이는 행과 열은 익숙하고 분석에 매우 유용하지만, **모든 데이터 활용 목적에서 유일한 정답은 아니다**. 계층과 옵션을 억지로 한 표에 넣으면 값이 반복되고, 여러 단계의 관계를 표로만 따라가면 JOIN이 복잡해질 수 있다. 반대로 정확한 합계가 필요한 데이터를 무조건 JSON이나 Graph로 저장하면 분석과 검증이 더 어려워질 수 있다.

이 장에서는 같은 패션 이커머스 기록을 관계형 데이터, 계층형 데이터, Graph 데이터로 표현해 보고, 각각의 대표 표현인 Table·JSON·Network를 비교한다. 목적에 맞는 원래 구조를 이해한 뒤 필요할 때 분석용 Table이나 다른 구조로 변환하는 관점을 익힌다.

> **이 장의 중심 질문**<br>
> 같은 고객·상품 기록을 언제 Table로, 언제 JSON으로, 언제 Network로 표현해야 할까?

## 생각해 보기: 장바구니 하나를 어떻게 저장할까?

고객 `C102`가 코트 한 벌과 셔츠 두 장을 장바구니에 담았다. 다음 세 질문은 같은 사건을 보지만 필요한 구조가 다르다.

| 질문 | 중요한 정보 | 먼저 떠올릴 구조 |
|---|---|---|
| 상품별 담긴 수량을 합산하려면? | 반복되는 행과 숫자 | Table |
| 고객의 장바구니 묶음을 API로 전달하려면? | 고객 아래 상품·옵션 목록 | JSON |
| 함께 관심을 보인 상품과 브랜드를 따라가려면? | 개체 사이 연결 | Network |

구조는 유행이나 도구 이름으로 고르는 것이 아니다. **무엇을 계산하고 전달하고 탐색할지**에 따라 선택한다.

## 학습 목표

이 장을 마치면 다음을 할 수 있다.

- Table·JSON·Network의 기본 구성 요소를 설명할 수 있다.
- 집계·중첩 정보·관계 탐색 중 질문에 알맞은 구조를 선택할 수 있다.
- 같은 데이터를 세 구조로 바꿀 때 유지되거나 사라지는 정보를 찾을 수 있다.
- Key, 중첩, Node와 Edge가 각각 어떤 역할을 하는지 설명할 수 있다.
- 실제 서비스에서 여러 구조를 함께 사용하는 이유를 설명할 수 있다.
- 구조 선택 시 분석 편의성뿐 아니라 메모리·저장 공간·검색 속도·변환 비용을 함께 검토할 수 있다.

## 핵심 용어

- **데이터 구조(data structure)**: 여러 값과 기록을 어떤 규칙으로 묶고 연결하는지 나타내는 방식.
- **관계형 표(relational table)**: 행과 열로 기록을 정리하고 공통 Key로 다른 표와 연결하는 구조.
- **Key**: 행 또는 개체를 식별하거나 서로 다른 데이터를 연결하는 값.
- **JSON**: 객체와 목록을 중첩해 옵션·목록·로그 같은 계층 정보를 표현하는 형식.
- **객체(object)**: 이름과 값의 쌍으로 묶인 정보.
- **배열(array)**: 순서가 있는 값 또는 객체의 목록.
- **Network·Graph**: 개체를 Node, 개체 사이 관계를 Edge로 표현하는 구조.
- **변환(transformation)**: 목적에 맞게 한 구조를 다른 구조로 펼치거나 묶는 작업.

## 왜 이 세 구조를 먼저 비교하는가

데이터 구조는 세 종류만 있는 것이 아니다. 배열, 시계열, 공간 데이터, 이미지 Tensor 등도 있다. 이 장에서 관계형·계층형·Graph 데이터 세 가지를 먼저 고른 이유는 패션 이커머스에서 자주 만나는 **기록, 포함, 연결**이라는 서로 다른 문제를 가장 간단하게 보여주기 때문이다.

- **관계형 데이터**는 고객 한 명, 주문 한 건처럼 반복되는 기록을 행으로 관리한다.
- **계층형·문서형 데이터**는 주문 안의 상품 목록이나 상품 안의 옵션처럼 포함 관계를 원래 묶음대로 표현한다.
- **Graph 데이터**는 고객이 상품을 보거나 상품이 브랜드에 속하는 것처럼 개체 사이 연결을 직접 표현한다.

이 셋을 비교하면 “데이터는 결국 Excel 모양이어야 한다”는 생각에서 벗어나, **활용 목적에 따라 원래 구조를 보존할지 분석용 표로 바꿀지** 판단하기 쉬워진다.

|---|---|---|---|
| 관계형 데이터 | Database Table, SQL 결과, pandas DataFrame | 행과 열 | 주문, 결제, 재고, 고객별 구매 횟수 |
| 계층형·문서형 데이터 | JSON 객체, API 응답, Document Database | 객체 안의 객체·목록 | 장바구니, 상품 옵션, API 응답, 행동 로그 |

## 2. 관계형 데이터: Table과 DataFrame으로 계산하기

관계형 표에서 행은 한 건의 기록, 열은 기록의 속성이다.

관계형 데이터는 구조의 원리이고 Table은 이를 보여주는 기본 단위다. 관계형 데이터베이스에서는 SQL로 Table을 저장·조회하며, 분석가는 조회 결과를 pandas `DataFrame`처럼 메모리 안의 표로 가져와 계산할 수 있다. Table과 DataFrame은 비슷하게 보이지만 DataFrame은 한 분석 프로그램의 메모리에 올라온 작업용 표현일 수 있다는 차이가 있다.

| customer_id | product_id | color | size | qty |
|---|---|---|---|---:|
| C102 | P501 | Navy | L | 1 |
| C102 | P320 | White | L | 2 |

이 구조는 다음 작업에 편리하다.

- `customer_id`별 구매·장바구니 건수 세기
- `product_id`로 상품 마스터와 JOIN하기
- 색상·사이즈별 수량 합산하기
- 중복 행과 누락 Key 확인하기

### Table에서 생기는 문제

한 주문에 상품이 여러 개이고 상품마다 옵션이 여러 개라면 한 행에 모두 넣기 어렵다. 정보를 반복해서 적거나 주문 표·주문 상품 표·상품 표로 나눠야 한다. 표를 나눌수록 중복은 줄지만 JOIN 조건과 Key 관리가 중요해진다.

| 흔한 문제 | 예 | 확인 방법 |
|---|---|---|
| Key 중복 | 상품 마스터에 P501이 두 행 | Key별 행 수 점검 |
| JOIN 누락 | 주문의 P999가 상품 표에 없음 | unmatched Key 목록 확인 |
| 행 수 증가 | 다대다 JOIN으로 주문이 복제됨 | JOIN 전후 행 수와 합계 비교 |
| 정의 불일치 | `price`가 정가인지 결제가인지 불명확 | 데이터 사전과 생성 규칙 확인 |

## 3. 계층형·문서형 데이터: JSON으로 묶음 보존하기

한 고객 아래 여러 상품이 있고 각 상품에 색상·사이즈·수량이 달린 모습을 그대로 전달하려면 JSON이 자연스럽다.

계층형·문서형 데이터는 구조의 원리이고 JSON은 이를 표현하고 전달하는 대표 형식이다. API는 JSON 문자열을 주고받을 수 있고, Document Database는 JSON과 비슷한 문서 단위로 데이터를 저장·검색할 수 있다. 따라서 JSON 파일 하나와 문서형 데이터베이스 전체를 같은 것으로 보아서는 안 된다.

```json
{
  "customer_id": "C102",
  "cart": [
    {
      "product_id": "P501",
      "product_name": "Oversized Coat",
      "color": "Navy",
      "size": "L",
      "qty": 1
    },
    {
      "product_id": "P320",
      "product_name": "Basic Shirt",
      "color": "White",
      "size": "L",
      "qty": 2
    }
  ]
}
```

JSON 문법을 외우는 것이 목적은 아니다. 객체 안에 목록과 다른 객체를 넣어 **원래의 묶음 관계**를 보존할 수 있다는 점이 핵심이다.

### JSON에서 생기는 문제

- 같은 의미의 필드가 `product_id`, `productId`, `item_id`처럼 달라질 수 있다.
- 어떤 상품에는 `size`가 있고 액세서리에는 없을 수 있다.
- 중첩이 깊어지면 상품별 집계와 품질 검사가 어려워진다.
- API 버전이 바뀌면 필드 이름과 구조도 달라질 수 있다.

분석하려면 `cart` 배열을 상품 한 건당 한 행으로 펼칠 수 있다. 이때 고객 ID가 각 행에 올바르게 반복되는지, 빈 장바구니가 사라지지 않는지 확인해야 한다.

## 4. Network·Graph 데이터: 관계 자체를 저장하기

고객과 상품, 상품과 브랜드처럼 **무엇이 무엇과 연결되었는가**가 질문의 중심이라면 Network 또는 Graph가 유용하다.

Graph는 Node와 Edge로 관계를 표현하는 구조이고, Network는 그 연결망을 가리키는 표현으로 자주 사용한다. 분석에서는 NetworkX 같은 도구로 메모리 안에서 다룰 수 있고, 서비스에서는 Graph Database에 저장해 여러 단계의 연결 경로를 조회할 수 있다.

```text
[C102]
  │
  ├── 구매 ── [P501 Coat] ── 소속 ── [Brand A]
  │
  └── 관심 ── [P711 Jacket] ── 분류 ── [Outerwear]
```

- 고객·상품·브랜드는 **Node**다.
- 구매·관심·소속·분류는 **Edge**다.
- Edge에는 구매 시각, 수량, 클릭 횟수 같은 속성을 붙일 수 있다.

그래프는 “C102와 비슷한 상품을 본 고객이 함께 구매한 브랜드는 무엇인가?”처럼 여러 연결을 따라가는 질문에 적합하다.

### Network에서 생기는 문제

연결이 많다는 사실이 곧 선호나 인과를 뜻하지는 않는다. 인기 상품은 거의 모든 고객과 연결되어 추천을 지배할 수 있고, 광고 노출이 많아서 연결이 늘었을 수도 있다. 관계의 종류·방향·시점과 연결이 생긴 원인을 함께 보아야 한다.

구조를 바꾸면 쉬워지는 일과 사라질 수 있는 정보가 동시에 생긴다.

| 변환 | 쉬워지는 일 | 잃거나 왜곡하기 쉬운 정보 |
|---|---|---|
| JSON → Table | 상품별 합계, JOIN, 필터 | 빈 목록, 중첩 순서, 원래 묶음 |
| Table → JSON | API 전달, 고객별 묶음 | 중복 행 처리 방식, 정렬 기준 |
| Table → Network | 경로·이웃·추천 탐색 | 원래 행의 세부 문맥과 분모 |
| Network → Table | 통계 요약과 모델 입력 | 복잡한 연결 구조와 경로 정보 |

변환 전후에는 다음을 비교한다.

1. 고객·주문·상품의 고유 개수가 같은가?
2. 수량과 결제 금액 합계가 유지되는가?
3. 빈 목록과 결측값이 사라지지 않았는가?
4. 중복 연결이 의도한 사건 수와 일치하는가?
5. 시간 순서와 관계 방향이 보존되는가?

## 6. 어떤 구조를 먼저 선택할까?

| 질문 | Table 우선 | JSON 우선 | Network 우선 |
|---|:---:|:---:|:---:|
| 상품별 매출을 정확히 합산한다 | ✓ |  |  |
| 상품 옵션 묶음을 API로 전달한다 |  | ✓ |  |
| 여러 연결을 따라 추천 후보를 찾는다 |  |  | ✓ |
| 공통 Key로 고객·주문을 결합한다 | ✓ |  |  |
| 서로 다른 모양의 이벤트 속성을 보존한다 |  | ✓ |  |
| 고객–상품–브랜드 경로를 설명한다 |  |  | ✓ |

구조를 고를 때는 질문 외에도 다음 조건을 확인한다.

- 데이터가 얼마나 자주 바뀌는가?
- 정확한 거래와 집계가 중요한가?
- 중첩 깊이와 필드 변화가 큰가?
- 관계를 몇 단계까지 탐색해야 하는가?
- 현재 조직이 운영·검증할 수 있는 저장소와 기술인가?
- 개인정보 삭제 요청과 접근 권한을 구조 안에서 추적할 수 있는가?

가장 복잡한 구조가 가장 좋은 구조는 아니다. 핵심 질문을 가장 단순하고 검증 가능하게 표현하는 구조에서 시작한다.

## 7. 분석 편의성뿐 아니라 메모리와 검색 속도 비교하기

구조 선택은 분석 코드가 편한지만으로 결정하지 않는다. 같은 정보를 어떤 구조로 저장하느냐에 따라 값의 반복, 인덱스 크기, JOIN과 문서 해석 비용, 관계 탐색 속도가 달라진다.

### 관계형 데이터

정규화하면 반복되는 값을 줄여 저장 공간을 절약할 수 있다. DataFrame도 숫자 컬럼은 비교적 효율적으로 저장하지만 문자열·객체 컬럼은 메모리를 더 사용할 수 있다. 인덱스가 있는 Key 조회, 조건 필터와 열 단위 집계에는 잘 맞는다. 반면 큰 Table 여러 개를 반복해서 JOIN하거나 여러 단계의 관계를 따라가면 처리 비용이 커질 수 있다.

### 계층형·문서형 데이터

관련 값을 한 문서에 모으면 JOIN을 줄일 수 있다. 고객 한 명의 장바구니 전체나 주문 한 건의 옵션 묶음을 ID로 읽는 작업에 유리할 수 있다. 다만 필드 이름과 중복 정보가 문서마다 반복되어 저장 공간이 늘 수 있고, 인덱스가 없는 깊은 중첩 필드를 찾거나 모든 문서를 가로질러 집계하는 작업은 느려질 수 있다.

### Network·Graph 데이터

Node와 Edge 외에도 연결 인덱스와 속성을 저장하므로 관계가 많을수록 부가 공간이 필요하다. 이웃 Node, 최단 경로와 여러 단계 연결을 탐색하는 작업에는 적합하다. 반대로 전체 거래 합계처럼 열을 넓게 읽는 집계나 Edge가 매우 많은 Graph를 적재하는 작업에는 더 많은 비용이 들 수 있다.

이 비교는 절대적인 속도 순위가 아니다. 실제 성능은 다음 조건에 따라 달라진다.

- 데이터의 행·문서·Node·Edge 수와 각 기록의 크기
- B-tree, Hash, 중첩 필드, 관계 인덱스 등 어떤 인덱스를 만들었는지
- 한 건 조회, 전체 집계, JOIN, 여러 단계 관계 탐색 중 무엇을 자주 하는지
- 메모리 안에서 계산하는지 디스크나 네트워크를 거쳐 읽는지
- 데이터 압축, 캐시, 동시 사용자와 업데이트 빈도

예를 들어 고객 한 명의 장바구니 전체를 자주 읽는 서비스라면 한 JSON 문서가 여러 Table JOIN보다 빠를 수 있다. 반대로 모든 고객의 상품별 매출 합계를 반복 계산한다면 열 중심의 Table이 더 단순하고 효율적일 수 있다. 고객–상품–브랜드 연결을 여러 단계 따라가는 요청은 Graph가 유리할 수 있지만, Edge와 인덱스를 유지하는 저장 비용이 추가된다.

따라서 작은 실제 표본으로 자주 사용할 질의를 실행해 **응답 시간, 최대 메모리, 저장 크기, 변환 시간과 결과 정확성**을 함께 측정한다. 하나의 기업이 원본 JSON, 거래용 관계형 Table, 추천용 Graph와 분석용 DataFrame을 함께 사용하는 이유도 각 구조가 잘하는 작업이 다르기 때문이다.

## 8. 생성형 AI가 구조를 제안할 때 검증할 것

생성형 AI는 JSON 예시, 테이블 스키마와 그래프 구조를 빠르게 제안할 수 있지만 실제 데이터의 규칙을 자동으로 아는 것은 아니다.

| AI 제안 | 반드시 확인할 것 |
|---|---|
| 테이블과 JOIN 코드 | Key의 고유성, JOIN 전후 행 수와 합계 |
| JSON Schema | 필수·선택 필드, 빈 배열, 버전, 타입 |
| 그래프 Node·Edge | 관계 방향, 시점, 중복 Edge, 개인정보 |
| 구조 변환 코드 | 누락된 기록, 펼친 행 수, 순서와 단위 |

고객 이름·주소·연락처 같은 실제 개인정보를 공개형 생성형 AI에 그대로 붙여 넣지 않는다. 합성 예시나 비식별 표본으로 구조를 설계하고 조직의 승인된 환경과 정책을 따른다.

## 짧은 활동: 한 사건을 세 구조로 표현하기

다음 사건을 Table, JSON, Network로 각각 간단히 표현한다.

> 고객 C102가 2026년 8월 22일 P501 Navy/L 한 개와 P320 White/L 두 개를 주문했다. P501은 Brand A의 Outerwear다.

세 표현을 다음 기준으로 작성한다.

- **Table:** 고객·주문·상품 Key와 수량을 포함한다. 이 표현으로 답하기 쉬운 질문과 어려운 질문을 하나씩 적는다.
- **JSON:** 고객 또는 주문 객체와 상품 배열을 포함한다. 중첩을 유지했을 때 쉬워지는 질문과 전체 집계처럼 추가 변환이 필요한 질문을 적는다.
- **Network:** 고객·상품·브랜드 Node와 관계 Edge를 포함한다. 연결 탐색에 적합한 질문과 열 단위 집계가 필요한 질문을 비교한다.

마지막으로 세 표현에서 고객 수, 상품 종류 수와 총수량이 일치하는지 확인한다.

## 이 장의 핵심

- Table은 집계와 정확한 JOIN, JSON은 중첩된 옵션·목록, Network는 연결과 경로 탐색에 적합하다.
- 세 구조는 경쟁 관계가 아니며 하나의 서비스 안에서 함께 쓰인다.
- 구조는 도구의 유행이 아니라 질문, 관계, 중첩과 검증 방법에 따라 고른다.
- 관계형·계층형·Graph 데이터는 구조 계열이고 Table·DataFrame, JSON 문서, Node–Edge Graph는 각각의 대표 표현·구현이다.
- 구조를 바꾸면 분석이 쉬워질 수 있지만 빈 목록, 순서, 묶음과 관계 문맥이 사라질 수 있다.
- 메모리와 검색 속도는 구조 이름만으로 결정되지 않으며 데이터 크기·인덱스·질의 유형을 기준으로 실제 측정해야 한다.
- 변환 전후에는 개수·합계·Key·결측·시간 순서를 비교해야 한다.
- 생성형 AI가 만든 스키마와 변환 코드도 실제 데이터 규칙과 작은 표본으로 검증해야 한다.
